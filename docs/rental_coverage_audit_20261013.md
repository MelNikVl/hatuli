После аудита также ужесточена идентификация ЖК в оценках: кроме
однозначного имени требуется совпадение официальной ссылки из объявления
с источником канонического ЖК или проверенной записью источника. Теперь
этот критерий общий для точного ЖК-индекса и `/compare`. **Baseline 63
строки получен по предыдущему, более широкому правилу имени**. Уменьшение
квалифицированного пула после смены правила нельзя интерпретировать как
сокращение рынка; сравнимы исходные count/freshness по категориям, а
eligible-пул нужно сравнивать по одному и тому же правилу идентификации.

Парковки и коммерция продолжают собираться в исходный каталог, но
автоматические месячные оценки для них отключены: карточки могут смешивать
ставки за час, месяц и м², а единица цены пока не хранится. Старые агрегаты
этих категорий удаляются при атомарной замене индекса; достоверные оценки
вернутся после явного хранения и проверки срока/единицы аренды.

Ещё 1 071 архивная квартира и 5 парковок имеют last_seen позднее archived_at,
но остаются inactive. Появление в валидной выдаче должно реактивировать
объявление; новый upsert устраняет эту проблему. История изменений цены
сохраняется. **Отдельного журнала архивных состояний аренды пока нет**:
реактивация очищает archived_at/archive_reason, поэтому по текущей таблице
нельзя восстановить все прошлые снятия и повторные появления. Для полного
исторического ряда потребуется миграция журнала состояний; сохранённые
дневные счётчики не заменяют историю каждого объявления.

## Как проверять охват и отделять сбой от движения рынка

1. **Задать границы.** Отдельные каталоги: квартиры месячной аренды,
   паркинг/гаражи, коммерция. Текущий сбор не охватывает дома, комнаты,
   посуточную аренду, другие города и площадки. «Весь рынок аренды» без этого
   определения — некорректное обещание.
2. **Сохранять доказательства обхода.** Для каждого типа: время начала/конца,
   независимый счётчик и последняя страница каталога в начале/конце,
   успешные страницы, сырые ID, число уникальных ID за круг, отклонённые
   карточки и причины. Завершение без прохода от страницы 1 не считается
   полным кругом; CAPTCHA/468/неизвестная страница не считаются концом.
3. **Учитывать движущуюся выдачу.** `страницы × 20` не равно числу уникальных
   объявлений: рекламные повторы, новые/удалённые карточки, перемещение
   выдачи. Показывать число уникальных ID и несовпадение с независимым
   счётчиком. Даже 100% по одному числу не гарантирует полноту при изменении
   каталога за круг.
4. **Независимая контрольная выборка.** Из обычного браузера проверить
   разные районы, комнатности и бюджеты, первые/средние/последние страницы.
   Для видимых ID проверить наличие в БД и last_seen. Контрольная выборка
   измеряет долю пропусков, но не доказывает 100% охват. Для точного
   сопоставления нужен разрешённый независимый список ID того же каталога.
5. **Собирать операционные счётчики.** Страницы/списковые запросы,
   детали/архивные запросы, 468 отдельно по контурам, доля успешных страниц,
   latency каждой стадии, новых/обновлённых/реактивированных/архивированных,
   последний успех по типу, подтверждённый круг и прогноз срока завершения.
   Дневные метрики описывают работу сканера, а не факт рыночной сделки.
6. **Не заменять отсутствие данных нулём.** Даты без здорового подтверждённого
   сбора помечать «неполное наблюдение»; их не использовать как падение
   спроса/предложения или тренировочные рыночные исходы. Ноль новых при
   нормальных страницах может быть реальным, но при пропущенных страницах
   ничего не говорит о рынке. Архив может естественно превышать приток:
   искусственная квота только скроет рынок, правильнее отдельный сигнал
   всплеска + проверка происхождения архива.

круга и не менее 95% уникальных ID относительно счётчика каталога. Даже
при выполнении этих условий полнота рынка остаётся `unknown`.

После развёртывания главный отчёт должен дополнить ≥30 минут реального

нужно явно называть прогнозом, не результатом полного прогона.
