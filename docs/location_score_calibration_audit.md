# Location Score — factor audit & calibration plan (без смены весов)

Задача 2026-08-18, "Property Identity — review calibration", Stage 4.
**Ни один вес/формула в `bot/core/location_score.py` этим документом не
меняется.** Инфраструктура (локальный OSM, дороги, парки, OSRM, таймеры)
не переделывается. Источник фактов — прямое чтение
`bot/core/location_score.py` (970 строк, уже хорошо задокументирован
собственными докстрингами) + прямые SQL-запросы к прод-БД, 2026-08-18.

## 1. Полная таблица текущих факторов

Модель — "пять latent-свойств" (не плоский список весов): каждое
свойство 0-100 из СВОИХ факторов, итог = Σ(вес_свойства × pct_свойства).
`_GROUP_WEIGHTS` (структурная константа, `bot/core/location_score.py:166`):

| Свойство | Вес | Факторы (диапазон) | Источник | source_quality | freshness |
|---|---|---|---|---|---|
| **transport** (Accessibility) | 25% | transit_stops (0..3) | OSM Overpass / local city_poi | 0.6 | periodic (был live) |
| | | lrt_access (0..4) | transport_hexes | 0.8 | periodic |
| | | road_access (0..2) | transport_hexes | 0.8 | periodic |
| | | route_connectivity (0..2) | transport_hexes | 0.8 | periodic |
| **infra** (Everyday infrastructure) | 25% | schools (0..2, вуз-only обычно) | OSM / local city_poi | 0.6 | periodic |
| | | amenities (0..4) | OSM / local city_poi | 0.6 | periodic |
| | | school_access (0..4) | astana_schools (160 строк) | 0.8 | manual |
| | | kindergarten_access (0..2) | astana_kindergartens | 0.8 | manual |
| **environment** | 20% | noise (-6..0) | OSM/local roads | 0.6 | periodic |
| | | parks (0..2) | OSM/local | 0.6 | periodic |
| | | air_quality (-3..0) | air_stations (реальный сенсор ПНЗ) | 0.8 | ? (не по таймеру описано) |
| **risk** (штрафная ось, 100 недостижим) | 15% | demolition (-2..0) | demolition_houses | 0.8 | manual |
| **urban_quality** | 15% | *(пусто)* | — | — confidence=0 структурно | — |
| **(вне групп, информационный)** | 0% | bank (0..0, всегда 0) | грубая эвристика по district | 0.2 | — |

**Confidence** — двухуровневый: на факторе (`_SOURCE_QUALITY`/`_FRESHNESS`/
`_PRECISION`) и на свойстве (`_group_confidence`, взвешенное по факторам
внутри свойства). "73/31%" читается как "измеренное даёт 73, но данных
мало" — НЕ "среда хорошая, мы уверены".

**Confidence НЕ равно "влияние на итог"** — свойство с confidence=20% всё
равно вносит полный вес (25%/25%/20%/15%/15%) в сумму, если хоть один его
фактор доступен (недоступные факторы исключаются из ДИАПАЗОНА свойства
целиком, `_is_available`, не считаются нулём — "Unknown ≠ average"). Т.е.
низкий confidence НЕ уменьшает вклад свойства в итоговый балл — это
раздельные оси (задача Stage 4 п.8 просит явно показать confidence
пользователю ИМЕННО потому, что итог сам по себе это не отражает).

## 2. Веса, выбранные экспертно и НЕ подтверждённые рынком

Явно, дословно из докстринга кода (`location_score.py:143`): "**Calibration
roadmap** (hedonic-регрессия ... + Bradley-Terry/conjoint) —
задокументирован в `docs/location_product_design.md` как БУДУЩАЯ работа,
явно НЕ реализуется". Т.е. код УЖЕ честно признаёт себя некалиброванным.
Конкретно:

- **`_GROUP_WEIGHTS`** (25/25/20/15/15%) — "структурная константа
  продукта" (комментарий в коде), выбрана человеком по аналогии с Walk
  Score/AreaVibes/JLL LQS benchmark, НЕ по регрессии на цену/DOM Астаны.
- **`_FACTOR_RANGES`** (min/max КАЖДОГО фактора внутри своей группы) —
  тоже экспертные, напр. `noise: (-6, 0)`, `demolition: (-2, 0)` — нет
  ссылки на калибровку "насколько -6 по шуму реально снижает цену/спрос".
- **`AI_SIMILARITY_THRESHOLD`-подобных порогов здесь нет**, но
  `_SOURCE_QUALITY`/`_FRESHNESS` тоже субъективные категориальные метки
  (0.8/0.6/0.2), не результат измерения "насколько этот источник реально
  предсказательный".
- **`bank` фактор** — диапазон (0,0), т.е. ВСЕГДА добавляет 0 — по факту
  чисто информационный (сам код это признаёт: `_INFORMATIONAL`), не
  участвует в итоговом баллe вообще, несмотря на наличие "грубой
  эвристики по district" за ним.

## 3. Метод калибровки (предложение, не реализовано)

**Целевая переменная — НЕ сырая цена.** Задача явно требует контроль
класса ЖК/площади/комнатности/возраста/периода — предлагается **price
residual**:

```
residual_i = log(price_i) − ŷ(rooms_i, area_i, floor_i, floors_total_i,
                              year_built_i, housing_class_i, complex_id_i,
                              month_i)
```

где `ŷ` — гедонистическая регрессия БЕЗ location_score в числе
предикторов (проект уже держит `hedonic_constants.py`/housing_class —
переиспользовать, не строить с нуля). `residual_i` — "сколько цена этой
конкретной квартиры отклоняется от объяснимого характеристиками", ПОСЛЕ
контроля за классом/площадью/комнатами/возрастом/месяцем.

**Шаг калибровки**: регрессия `residual_i ~ transport_pct_i + infra_pct_i
+ environment_pct_i + risk_pct_i` (urban_quality пуст, пропускается) —
коэффициенты этой регрессии = "насколько рынок В ДЕЙСТВИТЕЛЬНОСТИ платит
за каждый latent-property" — сравнить ЗНАК и ОТНОСИТЕЛЬНУЮ величину
коэффициентов с текущими `_GROUP_WEIGHTS` (25/25/20/15/15%). Совпадение
знака (transport/infra/environment положительны, risk отрицателен) —
sanity-check модели ДО пересмотра чисел; сама пропорция коэффициентов —
кандидат на новые веса (но смена весов — ОТДЕЛЬНОЕ решение, не этот PR).

**Дополнительные целевые переменные** (задача, явно все четыре):
1. **price residual** — выше.
2. **DOM/скорость ухода** — `outcome_labels.time_on_market` (уже
   считается), регрессия `time_on_market ~ group_pct_i + controls` —
   ожидаемый знак: хорошие transport/infra/environment -> МЕНЬШЕ DOM.
3. **Просмотры** — `apartment_listings`/`listing_snapshots.views` — то же
   как отдельная целевая (просмотры менее надёжны как "качество", больше
   как "видимость", но задача явно просит).
4. **Повторные размещения (relist)** — `outcome_labels.relisted_within_60d`
   (или, после Stage 2 merge design, property-level true_relist_count) —
   гипотеза: плохая локация -> чаще relist без продажи.

**Разрезы по районам и времени** (задача, явно) — регрессия ДОЛЖНА
включать district и месяц/квартал fixed effects (или отдельные прогоны по
периодам) — иначе коэффициент "transport" может на самом деле ловить
"это Есиль" или "это лето 2026", не транспорт как таковой.

**Явный запрет на простую корреляцию** (задача, п.4): сырой `corr(price,
transport_pct)` без контроля за площадью/классом/комнатами/возрастом —
НЕ используется нигде в этом плане ни как метод, ни как промежуточная
проверка "качества" — только residual после контроля.

## 4. Локальное покрытие дорог — проверено

`city_roads` (реальный SELECT, 2026-08-18):

| highway | строк |
|---|---|
| railway | 17 744 |
| secondary | 12 271 |
| tertiary | 10 085 |
| trunk | 7 029 |
| primary | 5 213 |
| motorway | 4 197 |

**Находка**: primary/secondary/tertiary — есть, все три требуемых класса
покрыты. **residential/service — ОТСУТСТВУЮТ ПОЛНОСТЬЮ** (0 строк любого
из этих highway-значений в таблице). Если фактор `noise` (score_layers/
noise.py, через `local_poi_near`) рассчитывает шум ТОЛЬКО от этих
классов (primary/secondary/tertiary/trunk/motorway), это, возможно,
осознанное решение ("шум от таких дорог значим, от дворовых проездов —
нет") — но НЕ подтверждено чтением `bot/score_layers/noise.py` в рамках
ЭТОГО документа (вне бюджета этого захода) — **флагуется как открытый
вопрос**, не факт: нужно явно прочитать noise.py и подтвердить, что
отсутствие residential/service — намеренное решение (шум важен только от
крупных дорог), а не пробел в live-Overpass fallback синхронизации
(`city-poi-sync.timer`). Про "никаких массовых live-запросов Overpass в
критическом пути" (задача, п.5) — подтверждено докстрингом самого
`location_score.py` (`_OSM_LAYERS` читают `local_poi_near`, Overpass —
только редкий fallback на несинхронизированную категорию, не в
critical path основного запроса).

## 5. Самал-парк / набережная — два разных эффекта (предложение)

Задача просит НЕ считать сезонный/вечерний шум и дневной отдых одним
и тем же эффектом. Сейчас `parks` (score_layers/parks.py) — один
фактор 0..2, без временнóй компоненты вообще (просто "есть парк рядом
или нет"). Предложение (НЕ реализовано):

- **`parks` остаётся** как есть — "положительный драйвер отдыха/
  притяжения", круглогодичный базовый бонус.
- **Новый штрафной под-фактор внутри `environment`** (не отдельная
  группа — тот же принцип "уточнение внутри свойства", которым уже
  объединили noise+green в environment) — `evening_noise_seasonal`:
  штраф ТОЛЬКО (а) в летние месяцы (май-сентябрь для Астаны) (б) в
  вечерние часы, ЕСЛИ рядом (тот же geo-радиус, что parks) есть крупный
  парк/набережная с известной вечерней посещаемостью. Источник данных
  под "известную посещаемость" СЕЙЧАС НЕ СУЩЕСТВУЕТ в проекте (не 2GIS
  popular times, не фактические жалобы) — это НОВЫЙ источник, который
  нужно либо найти бесплатно, либо честно оставить фактор
  "неизмеримым, confidence=0" (тот же принцип, что `urban_quality`).
- **НЕ постоянный круглогодичный штраф** — задача явно запрещает: если
  источника посещаемости нет, `evening_noise_seasonal` факторов не
  добавляется вообще, а не добавляется "средним" штрафом без данных.

## 6. Отзывы — где цепочка разорвана (проверено прямым SELECT)

```
reviews_raw:        5348 строк, из них classified_at IS NOT NULL: 483
                     (только ~9% вообще прошли сентимент-классификацию)
developer_reviews:  10387 строк (2GIS)
```

**Находка**: даже среди 483 строк с `classified_at` заполненным,
`sentiment` пуст у ВСЕХ (не NULL-safe проверка — буквально ни одного
непустого значения в выборке) — то есть шаг "классификация" СТАВИТ
timestamp, но НЕ записывает результат, ИЛИ сам sentiment_analyzer.py
пишет в другое поле/таблицу, не в `reviews_raw.sentiment` — конкретная
причина НЕ установлена в рамках этого документа (требует чтения
`sentiment_analyzer.py`/`reviews_pipeline.py` построчно, вне бюджета
этого захода) — **флагуется как находка, требующая отдельного
расследования**, не как решённый факт.

**location_score.py вообще НЕ ссылается на reviews/sentiment/developer
reputation/school ratings ни разу** (проверено `grep`) — вся ветка
отзывов/репутации застройщика/рейтингов школ (`astana_schools.rating`/
`rating_2gis` — колонки ЕСТЬ, используются ли они сейчас в
`school_access`-факторе или только хранятся — тоже не проверено в этом
документе) технически существует как СЫРЫЕ ДАННЫЕ, но НЕ доходит до
location_score ни через одно из пяти свойств.

**Нужный orchestration job** (предложение, не реализовано): новый
периодический шаг (тот же паттерн, что `city-poi-sync.timer`) —
`developer_reputation_snapshot` — агрегирует `developer_reviews`/
`reviews_raw` (после починки sentiment) в `developer_id -> reputation_
score` таблицу (аналог `seller_profiles`, НЕ location_score напрямую —
репутация застройщика относится к ЖК/зданию, не к локации участка) —
это, ВОЗМОЖНО, кандидат в `urban_quality` (пустая пока группа) как один
из её первых факторов, а не в существующие четыре.

## 7. Пользовательская расшифровка Location Score (предложение UI)

Задача, явно, 5 пунктов на КАЖДЫЙ фактор — код УЖЕ возвращает почти всё
нужное (`compute_complex_location_score()["group_scores"]`/
`["group_confidence"]`, факторы несут `source_quality`/`freshness` через
`_annotate_factor_metadata`) — предлагается ТОЛЬКО собрать уже
существующие поля в один читаемый блок, БЕЗ изменения самого расчёта:

```
🚇 Транспорт: 68/100 (уверенность: 62%)
  ▲ повышает: остановка в 200м (+2), LRT-доступность (+3)
  ▼ снижает: не измерено — route_connectivity недоступен для этого ЖК
  источник: OSM/city_poi (переиспользуемый слой) + transport_hexes (периодически обновляется)
  свежесть: обновлено city-poi-sync.timer на этой неделе
```

Структура на фактор: **почему получен балл** (сумма вклада каждого
доступного фактора со знаком), **confidence** (`_group_confidence`, уже
считается), **freshness** (`_FRESHNESS`, уже есть как категориальная
метка per-фактор), **источник** (текстовое имя источника — уже
комментарий в `_FACTOR_RANGES`, можно вынести в структуру данных, а не
только в комментарий). Это UI-задача (шаблон + небольшой рефактор
"комментарий -> структурированное поле" для источника фактора) —
НЕ требует изменения весов/формул, отдельный PR.
