# Стратегическая независимость от Krisha.kz

Дата: 2026-08-15. Статус: архитектурный контекст, НЕ план спринта с
датами — рамка для будущих решений, в частности для того, какие блоки
[`liquidity_model_design.md`](liquidity_model_design.md) и какие фазы
[`location_product_design.md`](location_product_design.md) приоритетнее
не только по AUC, но и по вкладу в независимость от одного источника.
Связь с [`verdict_strategy.md`](verdict_strategy.md) — этот документ
входит в контекст, который стоит держать в голове при планировании
Фазы C и последующих решений (см. ссылку в «Пауза по ML» в конце этого
захода).

---

## 1. Проблема

Сегодня ключевой входной поток данных Hatuli принадлежит другому
игроку:

```
V_0 = f(K)
```

где `K` — данные Krisha.kz (`apartment_listings`, `price_history`,
базовая идентичность ЖК через `complex_name`). Это не гипотетический
риск — это буквально видно по коду: `apartment_parser.py`/
`service_apartments.py` парсят Крышу как единственный источник
листингов, и почти вся ценность платформы (цена, площадь, продавец,
фото, описание) существует только потому, что Крыша это публикует.
Если доступ к Крыше исчезнет или радикально изменится (anti-bot,
смена вёрстки, юридическое ограничение, платный API) — вся текущая
ценность Hatuli останавливается в моменте.

Цель — не заменить Крышу (нереалистично и не нужно: она остаётся
крупнейшим агрегатором предложения), а сместить формулу ценности так,
чтобы отказ одного источника не был отказом всей платформы:

```
V_t = f(K, H, U, G, P, O)
```

- `K` — Крыша (сырое предложение)
- `H` — история (накопленные наблюдения Hatuli — цены, просмотры,
  снимки скора)
- `U` — пользователи (фидбек, поведение, в перспективе — свои
  объявления/данные)
- `G` — гео/гос источники (акимат, Казгидромет, OSM, госреестры)
- `P` — партнёры (агентства, застройщики — контролируемый B2B-канал)
- `O` — собственные признаки (вычисленные Hatuli, не существующие ни у
  кого ещё — скор, класс-модель, локационный скор)

Уже сегодня НЕ всё — `K`: снос (акимат), качество воздуха
(Казгидромет, см. аудит 2026-08-14), транспортная связность (OSM) —
первые ростки `G`. Дальше в этом документе — систематический разбор,
что уже сдвинуто и что сдвигать дальше.

## 2. Krisha Dependency Ratio (KDR)

```
KDR = (ценные поля, доступные ТОЛЬКО от Крыши) / (все ценные поля Hatuli)
```

Сейчас ~75%, цель — 50% через год, 30% через два года. **Это
стратегические ориентиры, не измеренные сегодняшние числа** — у
проекта пока нет формальной методологии «ценности поля» (одно дело —
`price` без альтернативы вообще, другое — служебная колонка вроде
`dup_marked_at`, которая не несёт рыночной ценности и не должна весить
столько же). Без такой методологии любой процент — на глаз.

**Иллюстрация метода (не официальный замер)** — грубая прикидка по
факту схемы БД на 2026-08-15: посчитаны колонки в двух Krisha-
происходящих таблицах (`apartment_listings` — 90, `complexes` — 75,
итого 165 — включая как сырые поля с Крыши, так и наши собственные
вычисления НАД ними, которые всё равно на 100% зависят от входа с
Крыши) против колонок в таблицах с независимым источником
(`air_stations` 10, `air_quality_astana` 11, `air_grid` 9,
`transport_hexes` 9, `demolition_houses` 12, `developers` 22,
`city_poi` 10 — итого 83; `complex_location_scores` и
`hex_market_stats` намеренно исключены из обеих сторон подсчёта — оба
вычисляются ИЗ Krisha-координат/Krisha-листингов, не независимы, хотя
`complex_location_scores` подмешивает и независимые OSM-факторы —
пограничный случай, не подсчитан ни туда, ни сюда):

```
наивный KDR = 165 / (165 + 83) ≈ 66.5%
```

**Явная оговорка**: это подсчёт КОЛИЧЕСТВА колонок, не их ЦЕННОСТИ —
одна колонка `price` весит для бизнеса больше, чем десяток служебных
`*_computed_at`/`*_checked_at` меток, а метод их уравнивает. Число
получилось в том же порядке, что заявленная оценка ~75%, что скорее
совпадение диапазона, чем подтверждение точности — **для реального
KDR нужна методология оценки ценности полей (например, вес по частоте
использования в скоринге/UI, а не единица на колонку), а не просто
подсчёт колонок**. Эта прикидка — только чтобы показать, как метод
МОГ бы считаться на живых данных, не как результат для принятия
решений.

## 3. Пять механизмов снижения зависимости

### 3.1 История как moat

```
Moat(t) ∝ ∫ observations dt
```

Чем дольше и плотнее Hatuli наблюдает рынок, тем ценнее становится его
СОБСТВЕННЫЙ архив — независимо от того, продолжает ли Крыша быть
источником новых данных. Конкурент с доступом к той же Крыше сегодня
не может купить историю за последний год — она либо накоплена, либо
нет. Уже работает: `price_history` (копится давно), `views_history`
(с 2026-08-14), `deal_score_snapshots` (ежедневно, с честной as_of-
семантикой), `complex_stats_history` (Г3). Каждый день простоя без
сбора — потерянная, невосстановимая точка на этом интеграле.

### 3.2 Property Graph

Объект недвижимости — не `listing_id`. Один и тот же физический объект
проходит через несколько объявлений (снят → перевыставлен → снова
снят), и сегодня они формально не связаны напрямую. Property Episode
ID (см. [`liquidity_model_design.md` §3](liquidity_model_design.md#3-property-episode-id))
— склейка `listing_id` одного объекта в постоянную сущность. Ценность
для независимости: чем полнее граф объектов, тем меньше платформа
зависит от того, что КОНКРЕТНО Крыша прислала сегодня — «память»
переживает отдельное объявление. Половина механизма уже есть
(`outcome_labels_recompute.py` — релист-детекция), не с нуля.

### 3.3 Данные без Крыши

Локация (Фаза L1 — `transport_hexes`/`demolition_houses`/OSM POI, уже
собирается независимо), юридические риски первички (БВУ/КЖК/МИО через
`developers.kz` — спроектировано в [`liquidity_model_design.md` §7](liquidity_model_design.md#7-юридические-риски-первички),
не собрано), качество воздуха (`air_stations`/`air_quality_astana` —
уже собирается годами, не интегрировано в скоринг, см. аудит
2026-08-14). Общая черта — данные о МЕСТЕ и КОНТЕКСТЕ, не о конкретном
объявлении, поэтому Крыша тут в принципе не нужна как посредник.

### 3.4 Пользователь как датчик

Waze-модель: не полагаться только на то, что видит платформа сама, а
собирать сигнал от людей, которые физически взаимодействуют с рынком —
фидбек по алертам (`alert_feedback`, см. `verdict_strategy.md` §7,
Часть 4 `scoring_roadmap.md`) как первый шаг. **Честно**: этот механизм
СЕГОДНЯ не построен — Часть 4 («Персональные телеграм-алерты») в
очереди, не начата. Указан здесь как направление, не как факт.

### 3.5 B2B-инверсия

Вместо того, чтобы Hatuli всегда ТЯНУЛ данные с Крыши, агентства/
застройщики МОГУТ подключить свой фид напрямую к Hatuli (эксклюзив на
новостройки, актуальность без задержки парсинга, свои данные о
статусе бронирования). Это разворачивает направление потока: не
Hatuli зависит от чужого сайта, а поставщики предложения зависят от
дистрибуции через Hatuli. В коде прецедента нет вовсе — чистая
гипотеза трека, не проверенная ни с одним партнёром.

## 4. Bayesian эффект

```
Posterior = Prior (история Hatuli) × Likelihood (текущие данные Крыши)
```

Рамка мышления, не формула для реализации: чем длиннее и плотнее
собственная история (`Prior`), тем меньше веса в итоговом выводе несёт
именно СЕГОДНЯШНИЙ полный снимок рынка с Крыши (`Likelihood`). На
раннем этапе (мало истории) Hatuli практически равен Крыше —
любой перебой фатален. С годами накопления та же формула должна
продолжать выдавать разумные оценки даже при частичном/деградировавшем
доступе к свежим данным — потому что prior уже несёт большую часть
информации о том, «как обычно ведёт себя этот ЖК/район/сегмент».
Прямое обоснование того, почему §3.1 (история как moat) — самый
дешёвый и уже работающий механизм: он не требует новых интеграций,
только время и дисциплину сбора.

## 5. Позиционирование

**Не** «где найти квартиру» — в этой гонке Крыша побеждает по
определению (она и есть основной источник предложения, у неё сетевой
эффект продавцов). **А** «где проверить квартиру перед покупкой» —
Carfax для квартир Казахстана. Пользователь приходит С ОБЪЕКТОМ сам
(нашёл его где угодно — на Крыше, у агента, по сарафанному радио),
Hatuli проверяет историю/риски/рынок вокруг него.

Это позиционирование уже частично на что-то опирается: объяснимость
вердикта — уже сильная сторона текущего UI (не голое число, причины —
`scoring_audit.md` §4), локационный блок Фазы L2 — уже показывает «что
я реально получаю, покупая здесь» отдельно от цены. Разница с текущим
состоянием — сегодня это позиционирование НЕ заявлено явно
пользователю (страница объявления — витрина деталей и торга, не явно
framed как «проверка»), но архитектурно уже к нему близко.

Проверено по коду/БД на 2026-08-15, не принято на веру:

| Поле | Krisha | Hatuli (свои данные) | Альтернативный источник |
|---|---|---|---|
| Цена | ✅ единственный источник (вторичка) | `apartment_listings.price` (копия) | 🟡 частично — для НОВОСТРОЕК уже есть `homeportal.kz`/`korter`/`homsters` (`complexes` cx_sources, `complex_detail.html`); для вторички — нет альтернативы вовсе |
| Площадь | ✅ единственный источник (вторичка) | `apartment_listings.area` (копия) | 🟡 та же новостройка-оговорка, что у цены |
| ЖК (идентичность) | ✅ основной источник имени | `complexes` (Entity Resolution над Крышей) | 🟡 для новостроек — homeportal.kz/korter/homsters независимо перечисляют ЖК; для старого фонда/вторички — нет независимого реестра |
| DOM (срок экспозиции) | ✅ единственный источник (`first_seen`/`archived_at`) | `outcome_labels`/`complex_stats_history.avg_dom_days`/`turnover-dynamics` | 🔴 нет — DOM по определению меряет время НА Крыше, другой источник давал бы другое число, не то же самое |
| Relists (повторные листинги) | ✅ единственный источник сигнала | `outcome_labels_recompute.py` (внутренняя детекция) | 🔴 нет — целиком внутренняя эвристика над Крышей, ничего независимого |
| `price_history` | ✅ единственный источник | Собственная таблица, копится давно, уже сильная | 🔴 нет прямой альтернативы; косвенно — БВУ/КЖК истории для новостроек (не собрано) |
| Ликвидность (скор) | — | Полностью собственное вычисление (`price_score`/будущая liquidity-модель) | ➖ не применимо — это НАШ продукт, не заимствованный факт, но построен НАД Krisha-данными (цена/DOM), так что косвенно зависим |
| `location_risk` | — | `complex_location_scores`/`hex_market_stats` (Фаза L1) | ✅ факторы независимы (OSM/акимат/Казгидромет; с 2026-08-15 ещё точнее — `astana_schools`/`astana_kindergartens`, источник — astana-bilim.kz/сайты организаций, 160/131 строка, `_schools_factor()`/`_kindergartens_factor()`) — **но** координата, К КОТОРОЙ их привязывают, всё ещё резолвится из Krisha-листингов (`resolve_complex_geo_centroid`) — без Крыши новый ЖК физически негде взять координату |
| `legal_status` (БВУ/КЖК/МИО) | — | Не собрано | ✅ полностью независимый источник (`developers.kz`), спроектировано, не реализовано |
| Отзывы жильцов | — | `complexes.residents_notes` — **есть, но почти не заполнено**: 3 из 2131 записей на 2026-08-15 (0.14%) | ✅ по происхождению независимо (ручной ввод админом через `/complexes`, не скрейпинг Крыши) — но как источник сигнала пока не работает из-за объёма |

**Общая картина**: реальная независимость уже есть только там, где
Hatuli либо (а) вычисляет что-то ЦЕЛИКОМ своё поверх чужого сырья
(скоринг), либо (б) подключил внешний контекстный источник (гео,
воздух, снос). Базовые факты сделки (цена, площадь, DOM для вторички)
не имеют независимой альтернативы в принципе, не только «пока не
подключили» — единственный путь снизить зависимость по НИМ — не
замена источника, а B2B-инверсия (§3.5) или собственный поток
объявлений от партнёров.

## 8. Метрики отслеживания

- **KDR** — ежегодно, как только появится методология оценки ценности
  поля (не подсчёт колонок, см. §2).
- **Доля полей с альтернативным источником** — из таблицы §6, доля
  строк с ✅/🟡 против 🔴 — можно считать хоть сейчас как первый срез
  (сегодня: 4 из 10 полей в таблице §6 имеют хоть какую-то
  независимость — ✅/🟡, 6 — нет).
- **Глубина истории** (средний возраст `observations`) — считаемо уже
  сегодня из `first_seen`/`fetched_at` по каждой из таблиц §3.1 — не
  делалось ни разу, первый замер был бы полезен как baseline.
- **Доля user-generated данных** — сегодня фактически 0% (Часть 4 не
  начата, `residents_notes` заполнено на 0.14% и не user-generated в
  строгом смысле — это ввод админа, не массового пользователя).
