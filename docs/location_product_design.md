# Локация как продуктовая ось — архитектура и дизайн

Дата: 2026-08-14. Статус: черновик к продуктовому треку (не код, не
спринт-план с датами — очередь работ в конце документа). Связка с
остальной стратегией — [`verdict_strategy.md`](verdict_strategy.md), в
частности [«Пауза по ML»](verdict_strategy.md#пауза-по-ml-2026-08-14--2026-09-14):
этот трек — один из двух разрешённых во время паузы Фаз C/D.

Этот документ — НЕ код. Он фиксирует продуктовую гипотезу, что видит
пользователь, какие риски недвижимости мы реально способны вычислить на
имеющихся данных, что для этого есть/не хватает и в каком порядке это
имеет смысл делать. Реализация — отдельные заходы по фазам L1-L4 ниже,
каждая со своим гейтом (тот же принцип §8 `verdict_strategy.md`: цифры
до/после, не «выглядит полезным»).

---

## 1. Продуктовая гипотеза

Hatuli сейчас отвечает на один вопрос: **«дорого или дёшево относительно
рынка?»** (`price_score`/`score_total`, гексагон+кольцо+ЖК median). Это
вопрос про цену конкретного объявления — полезный, но узкий: он ничего
не говорит о том, что покупатель реально получает за эту цену, кроме
самой квартиры.

Локация добавляет второй вопрос: **«что я реально получаю и какие риски
беру, покупая именно здесь?»** — шум, снос по соседству, транспортная
изоляция, насыщенность предложением (перекупленный район), деградация
района во времени. Это вопросы не о цене, а о месте — они не
конкурируют с `price_score`, а покрывают то, что он структурно не может
покрыть (два объявления с одинаковой ценой/м² в одном гексагоне могут
стоять на противоположных полюсах по факту риска — рядом со сносимым
цехом или рядом с парком).

**Это превращает Hatuli из агрегатора объявлений в систему due
diligence недвижимости** — не «вот список квартир по фильтрам», а «вот
конкретная квартира и всё, что мы можем честно сказать о риске жить
именно здесь». Тот же принцип объяснимости, что уже действует в
скоринге (`scoring_audit.md` §4: сила текущего UI — не число, а
причины) — локационный анализ обязан объяснять, а не давать голый скор.

Явно НЕ цель: замена риэлтора/юриста, оценка юридической чистоты сделки,
прогноз роста цены района (это ближе к Фазе C outcome-моделям, не к
этому треку — локационные данные ниже готовятся как ВХОД для неё, не
как самостоятельный прогноз, см. §6).

## 2. Что видит пользователь

### Карточка ЖК — новый блок «Локация»

Встраивается в существующую страницу ЖК (`/complex/{id}`, `complex_
detail.html`) рядом с уже там живущим `location-score` API-вызовом
(backlog #31, `bot/core/location_score.py`) — не отдельная страница,
блок на той же. Причина: пользователь уже здесь смотрит на конкретный
ЖК, переход на отдельный URL — лишний клик без выгоды.

Структура блока (сверху вниз, от общего к частному):

1. **Скор-карта** — та же 0-100 шкала, что уже даёт
   `compute_complex_location_score()`, но с явной раскладкой по группам
   факторов (не один слитный балл): 🚏 транспорт, 🏫 инфраструктура,
   🔇 шум, 🌳 зелень, ⚠️ риски (снос/перенасыщение/деградация — новые
   факторы, см. §3). Каждая группа кликабельна → раскрывает список
   конкретных находок (уже есть паттерн в `location_score.py` — факторы
   с человекочитаемыми label, просто сейчас не сгруппированы визуально).
2. **Карта с слоями** — переиспользует существующую карту (та же, что
   `/admin/api/map-points`), добавляются переключаемые слои: POI
   (школы/сады/остановки/магазины — уже в `score_layers/`), зона сноса
   (`demolition_houses`, если есть в радиусе), тепловая карта плотности
   предложения (новый агрегат, §3). Слои — чекбоксы, не все включены по
   умолчанию (карта не должна превращаться в кашу).
3. **Риск-бейджи** — короткие текстовые плашки под скор-картой, тот же
   визуальный паттерн, что уже есть у "недооценено"/"высокая доходность"
   в модалке объявления (`bot/core/listing_detail.py`): «🏗️ снос в
   400м (2027)», «📈 предложение выросло на 40% за квартал», «🐌 срок
   экспозиции растёт» — только когда есть основания, не пустая плашка
   «рисков не найдено» (Unknown ≠ average здесь тоже — нет данных, нет
   плашки, а не зелёная галочка).
4. **Таймлайн развития района** — простой линейный график по
   `complex_stats_history` (уже собирается, Г3) — медианная цена/м² и
   `listings_count` по месяцам для этого ЖК/дома, с явной пометкой на
   оси «доступно с 2026-08-14» (не выдумываем историю до начала сбора).

### Что НЕ делается на первой итерации

Единый «общий скор локации, заменяющий всё» — намеренно не строится
одним числом; текущий отдельный `location-score` уже даёт агрегат, но
блок riск-бейджей/таймлайна — это дополнение, не переупаковка в другую
цифру. Причина та же, что и в вердикт-стратегии (§3.3 `score` —
интерфейс модели, не сама модель) — больше цифр без объяснения хуже,
чем меньше цифр с объяснением.

## 3. Какие риски недвижимости мы способны вычислять

| Риск | Есть данные? | Источник | Качество сигнала |
|---|---|---|---|
| Шум (магистрали, ж/д) | ✅ есть | OSM Overpass, `score_layers/noise.py` | Прямое расстояние до трасс — грубо, но работает |
| Снос по соседству | ✅ есть | `demolition_houses` (акимат, вручную собранная база) | Точечные случаи, не полное покрытие города |
| Транспортная изоляция | ✅ есть | `transport_hexes` (`hype_tracker`) — LRT/автобусы/дороги/развязки | Хорошее покрытие, но без частоты рейсов |
| Перенасыщение предложением | 🟡 частично | `apartment_listings` — можно агрегировать плотность объявлений по гексагону/ЖК, сейчас не считается | Нужна агрегация, данные для неё уже есть |
| Деградация района (рост DOM, доля снижений цены) | 🟡 частично | `complex_stats_history` (Г3) + `price_history` — можно вывести тренд, копится с 2026-08-14 | Нужно ≥30-60 дней истории для тренда, не мгновенно |
| Экология / воздух | 🟡 частично | инфраструктура есть (`air_stations`/`air_quality_astana`/`air_grid` — см. §4), интеграция в `location_score` не выполнена | Тепловая карта уже есть в дашборде («Воздух (ПНЗ)»), но не как фактор скора ЖК — кандидат Фазы L3 |
| Ходьбо-доступность (walkability) | 🔴 нет по-настоящему | сейчас прямое расстояние (`haversine_km`), не маршрут по дорогам | Прямая линия занижает реальный риск изоляции (река/забор/трасса режут кратчайший путь) |
| Качество школ (не просто «рядом есть школа») | 🟡 частично, задача 2026-08-15 | `astana_schools`/`astana_kindergartens` — точное расстояние + тип (НИШ/международная/лицей/гимназия vs общеобразовательная) как прокси качества, `bot/core/location_score.py::_schools_factor()`/`_kindergartens_factor()` | Тип — грубый прокси качества, не рейтинг; `rating` в таблицах 0% заполнена, нет источника (2GIS не подключён) — см. §4 |
| Планы застройки (будущая плотность/стройки рядом) | 🔴 нет | сайт акимата, Генплан — не парсится | Ручной сбор пока (как `demolition_houses`) |

Не претендуем на факторы, для которых нет честного источника —
принцип Unknown ≠ average действует и здесь: риск, который мы не можем
измерить, не подменяется нейтральной оценкой, а просто не показывается.

## 5. Технические решения

- **Хранить, а не считать live.** Новая таблица `complex_location_
  scores` (по аналогии с уже существующим паттерном `complex_stats_
  history`/`deal_score_snapshots`) — `complex_id`, факторы по группам,
  `computed_at`. Живой `/admin/api/complex/{id}/location-score` уже
  существует и продолжает работать для интерактивного пересчёта по
  запросу (пользователь открыл карточку впервые) — но регулярный
  пересчёт для уже просмотренных ЖК идёт по таймеру в эту таблицу, не
  на каждый заход в карточку.
- **Кэш OSM по районам, не live Overpass на каждый запрос.** Публичный
  Overpass — общий rate-limit на весь Казахстан, не только на этот
  проект (уже отмечено в `location_score.py` докстринге как
  осознанное ограничение — «без Yandex/2GIS API»). Кэш на уровне
  района/гексагона (не на уровне ЖК — соседние ЖК в одном районе видят
  почти одинаковые POI) с обновлением раз в неделю — резко снижает
  число запросов и защищает от таймаутов на живой странице.
- **Агрегация рыночных метрик по локации** (плотность предложения,
  DOM, доля снижений) — считается пакетно (тот же ежедневный таймер,
  что уже пишет `complex_stats_history`/`deal_score_snapshots`), не по
  запросу; агрегация по гексагону, не только по `complex_id`, — риск
  «перенасыщения» это свойство района, не конкретного ЖК.
- **`resolved_house_id` учитывается везде**, где агрегация идёт по
  `complex_id`/координатам дома под зонтиком — тот же урок, что уже
  зафиксирован для геоцентроида (`house_resolution.py`) и `complex_
  stats_history`: без этого учёта агрегаты домов-зонтиков либо пустые,
  либо считаются по чужим координатам.
- **Семантика итогового 0-100 — взвешенное среднее по группам, не
  линейная сумма** (задача 2026-08-15, "Location Reliability Phase",
  `bot/core/location_score.py::normalize_group_weighted()` —
  канонический источник формулы и её ограничений, не дублируется
  здесь). Веса групп фиксированы структурно (transport 25% / infra
  25% / green 20% / noise 15% / risk 15%) и НЕ зависят от того,
  сколько факторов сейчас заведено внутри каждой — так добавление
  нового фактора не может задним числом просадить нормализованный
  score ВСЕХ уже посчитанных ЖК только из-за расширения знаменателя
  (живой баг, пойманный при добавлении school_access/kindergarten_
  access 2026-08-15: 66 -> 55 без единого содержательного изменения
  для конкретных ЖК — так больше не должно повторяться).
- **OSM-слой schools больше не дублирует astana_schools/kindergartens**
  (та же фаза, коммит "двойные школы + building_age") — когда точные
  факторы `school_access`/`kindergarten_access` реально посчитаны
  (обычный случай — astana_schools/kindergartens покрывают весь город),
  OSM-слой `bot/score_layers/schools.py` зовётся в режиме
  `university_only=True` и считает ТОЛЬКО вузы (их нет ни в одной из
  двух точных таблиц) — раньше один и тот же школьный сигнал
  засчитывался дважды с двух источников. Дефолтное поведение слоя (для
  остальных потребителей — per-listing скоринг) не изменилось.
- **`building_age` убран из location score** (та же фаза/коммит) —
  возраст здания это качество КВАРТИРЫ/ЗДАНИЯ, не локации: два соседних
  дома на одной точке карты (один 2025 года, другой 1980-го) должны
  иметь одинаковый location score. Функция `_building_age_factor()`
  сохранена в коде как есть — кандидат для будущего
  property_score/structural-quality скора, который считается по
  ЖК/квартире, не по локации.
- **Confidence переработан + диапазон группы теперь availability-aware**
  (та же фаза, коммит "Confidence", `bot/core/location_score.py::
  _is_available()`/`_group_range_available()`/`_compute_confidence()` —
  канонический источник, не дублируется здесь). Закрывает оба известных
  ограничения предыдущих коммитов фазы: диапазон группы теперь строится
  только из РЕАЛЬНО измеренных для конкретного ЖК факторов (не
  статическая схема) — группа без единого измеренного фактора честно
  вносит 50% (не 0%, как раньше для transport/infra/green). Сам
  confidence взвешен по надёжности ИСТОЧНИКА (`_SOURCE_QUALITY` — точный
  реестр 0.8 / OSM 0.6 / эвристика 0.2), не по плоской доле "посчитано/
  не посчитано" — два ЖК с одинаковым КОЛИЧЕСТВОМ измеренных факторов, но
  из источников разного качества, теперь получают разный confidence.

## 6. Связь с будущей Фазой C

Локационные данные, которые здесь строятся, — не отдельный продукт для
показа и всё; это одновременно будущие **признаки для outcome-модели**
(предсказание ликвидности/риска, не цены — см. переосмысленную Фазу C в
[`verdict_strategy.md`](verdict_strategy.md#фаза-c-недели-5-6--лестница-моделей)).
Прямая связка:

- Транспорт/школы/шум/зелень (уже посчитанные факторы `location_score`)
  → признаки «качество места».
- Плотность предложения, DOM-тренд, доля снижений (новые в §3/§5) →
  признаки «рыночное давление района», по духу то же самое, что
  `views_velocity`/`seller_type` в списке кандидатов Фазы C.
- Снос/деградация → признаки «структурный риск», не заменяемые ценовыми
  сигналами вообще (`price_score` в принципе не может увидеть «через
  два года тут будет стройплощадка»).

Это значит: фаза L1 (см. §7) должна проектировать схему `complex_
location_scores`/агрегатов рыночных метрик так, чтобы её можно было
читать как признаки моделью Фазы C напрямую (числовые колонки,
`computed_at` для temporal-safety — тот же принцип `as_of`, что уже
проведён через `deal_score.py`/`comparable_score.py`), не переделывать
формат задним числом.

  + агрегация рыночных метрик по гео (плотность/DOM/доля снижений) —

  Backfill `complex_location_scores` по ~2079 ЖК с координатами
  выполняется в фоне независимо от кода/коммитов (36/2079 на момент
  записи, публичные зеркала Overpass нестабильны — первый полный охват
  занимает часы) — закроется автоматически, механизм готов и
  протестирован, ждать его для старта L2 не нужно.
- **Фаза L2 — ✅ ЗАВЕРШЕНА 2026-08-14.** UI карточки ЖК с локационным
  блоком (§2) на `/complex/{id}` — новый блок «🗺 Локация»,
  ДОПОЛНЯЕТ существующую страницу, ничего живого не меняет (карточка
  «Что рядом»/`location-score`, карта-точка, price-dynamics/turnover-
  dynamics графики — как были). Все 4 части плана: скор-карта по
  группам (transport/infra/noise/green/risk), риск-бейджи (снос + доля
  снижений цены ≥20%), карта со слоями (POI/снос/плотность,
  переиспользует существующий Leaflet instance), таймлайн `price_drop_
  share_30d` (hand-rolled SVG, тот же паттерн, что уже есть на
  странице). Один новый эндпойнт — `/admin/api/complex/{id}/location-
  detail`, логика в `bot/core/complex_location_detail.py` (роут не

  [`scoring_roadmap.md` Часть 10](scoring_roadmap.md#часть-10-продуктовый-трек-локация-фаза-l2-ui--✅-завершена-2026-08-14).
