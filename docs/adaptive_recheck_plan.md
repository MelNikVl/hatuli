# Adaptive recheck — расчёт на бумаге (2026-08-13)

Задача: пересчитать стратегию re-check'а активных объявлений
(`bot/core/archive_check.py`, вызывается из `service_apartments.py::run_cycle()`)
под цели — **круг <24ч, hot ≤6–12ч, бюджет запросов ≤ текущего**. Числа
ниже — из реальной БД/`app_settings` на момент расчёта (2026-08-13), не
предположения. Код не пишется в этом проходе — только цифры и решение,
что считать "hot"/"cold" и как это ложится в текущий бюджет.

## 1. Текущее состояние (измерено)

| метрика | значение | источник |
|---|---|---|
| активных объявлений | **42 020** | `apartment_listings WHERE is_active IS NOT FALSE` |
| никогда не проверялись на архив | **34 983 (83%)** | `archive_checked_at IS NULL` |
| `ARCHIVE_CHECK_BATCH` (детальных проверок/цикл) | **40** | `app_settings` |
| циклов `run_cycle()` в сутки | **~22** | `sleep(random(50,80) мин)` → 24×60/65 |
| **текущий бюджет детальных archive-check запросов** | **≈880/сутки** | 40×22 |
| **круг** при текущем темпе (42020/880) | **≈48 суток** | — далеко не 24ч |
| очистка одного бэклога "никогда не проверенных" (34983/880) | **≈40 суток** | — |
| архивируется в сутки (реальная текучесть) | **51–63/сутки** | `archived_at > now()-24h`: 63; 7-дневное среднее: 51.3 |
| krisha.kz общий бюджет/цикл (fresh 8 стр + deep sweep 36 стр + detail-fetch до 60×2 + archive-check 40) | **84 гарантированно + до ~120 условно = 84–204/цикл** | `PARSER_MAX_PAGES`, `DEEP_SWEEP_BATCH`, `DETAIL_FETCH_BATCH`, `ARCHIVE_CHECK_BATCH` в `app_settings` |
| deep-sweep круг каталога (отдельная, уже мерящаяся метрика) | **271 500 с ≈ 75.4 ч ≈ 3.14 сут** | `DEEP_SWEEP_CIRCLE_DURATION_SEC` |
| всего страниц каталога (33196 объявл. / 40 на стр.) | **≈830** | `KRISHA_TOTAL_FOUND` |

**Вывод №1**: буквально "детально перепроверить каждое из 42020 активных
объявлений за 24ч" физически не влезает даже в теоретический максимум
одного воркера на текущем темпе вежливости (2.5–5с/запрос, среднее
3.75с → ≤960 запросов/час макс. НЕПРЕРЫВНО, 24/7, без единой минуты на
что-то ещё) — 42020/960 ≈ 43.8 ч > 24ч. Дорогая точечная проверка
(detail-page, 1 запрос = 1 объявление) в принципе не может дать круг
<24ч на текущем размере активной базы без роста темпа/параллелизма —
а рост темпа прямо противоречит цели "бюджет ≤ текущего". Значит "круг
<24ч" не может значить "детально проверить всех" — нужен более дешёвый
сигнал для холодной массы, и точечная проверка — только для горячей.

## 2. Что на самом деле означает "круг" — переосмысление

Два разных сигнала архивации, разные по цене:
1. **Присутствие в каталоге** (deep sweep, уже существует) — 1 запрос =
   **40 объявлений** (страница выдачи). Дёшево. Не подтверждает
   архивацию напрямую, но: если объявление, которое раньше видели,
   не встретилось НИ НА ОДНОЙ странице за целый круг каталога — сильный
   косвенный сигнал "вероятно ушло".
2. **Детальная страница объявления** (`archive_check.py`) — 1 запрос =
   **1 объявление**. Дорого, но авторитетно (прямой бейдж "в архиве"/404).

Текущая система использует ТОЛЬКО (2) для архивации, и вообще не
использует то, что (1) уже покрывает всю базу для *других* целей
(поиск новых объявлений) — те же данные, которые уже качаются, не
используются как сигнал ливости существующих.

**Решение**: (1) — основной, дешёвый сигнал для холодной массы; (2) —
дорогой, authoritative, только для (а) горячего пула на регулярной
основе и (б) подтверждения "пропало из каталога"-кандидатов от (1)
перед тем, как реально проставить `is_active=FALSE` (защита от шума
ре-ранжирования Крыши — объявление может временно не попасть в текущий
срез страниц без реальной архивации).

## 3. Hot/cold — размеры по реальным данным, не догадке

Проверил гипотезу "hot = новое" на факте (2344 архиваций за 30 дней с
известным `first_seen`):

| возраст на момент архивации | доля |
|---|---|
| ≤3 дня | 175 (7.5%) |
| 3–14 дней | 805 (34.3%) |
| >14 дней | 1364 (**58.2%**) |

**Гипотеза отвергнута**: большинство архиваций случается у объявлений
СТАРШЕ 2 недель, не у свежих — "новизна" не концентрирует текучесть,
не годится критерием "hot".

Вместо этого — **score_total** (уже существующий, уже используется как
tie-break в `check_archived()`, отражает "что реально показываем
пользователю первым"): показ устаревшего/проданного объявления в топе
— реальный UX-урон, в хвосте — почти никто не увидит.

| порог score_total | кол-во активных |
|---|---|
| ≥95 | 12 |
| ≥90 | **172** |
| ≥88 | 580 |
| ≥85 | 1 931 |
| ≥80 | 4 338 |

**Бюджетное ограничение сверху** (при цели "бюджет ≤ текущего" ≈880/сут
детальных проверок): hot-пул × частота ≤ 880. При частоте 4×/сутки
(раз в 6ч) — максимум **220** объявлений в hot; при 2×/сутки (раз в
12ч) — максимум **440**.

**Выбор: score_total ≥ 90 → 172 объявления.** Помещается в 6-часовую
цель с запасом: 172 объявления / `ARCHIVE_CHECK_BATCH`=40 в приоритете
= круг за **5 циклов** (~5×65мин ≈ **5.4 ч**, лучше цели 6–12ч). Расход
бюджета: 172×4 (реалистично ~4.4 круга/сутки при 5.4ч на круг) ≈ **760
детальных запросов/сутки** — под текущим потолком 880, оставляет **~120
запросов/сутки** на подтверждение cold-кандидатов + добор бэклога.

Cold-пул = остальные **37 682** (89.7%) активных — НЕ на индивидуальной
детальной проверке вовсе, только на дешёвом каталожном сигнале (п.2).

## 4. Cold-круг через каталог — бюджет и срок

Всего страниц каталога: **≈830**. Текущий `DEEP_SWEEP_BATCH`=36
стр/цикл × 22 цикла/сутки ≈ **792 стр/сутки** → теоретический круг
830/792 ≈ **1.05 суток (25.2 ч)** — на 5% дольше цели.

**Реально измеренный** круг — 75.4 ч (3.14 сут), **втрое дольше**
теории. Разбирался: код детектирует "конец круга" по "в батче нет
новых id" (`unravel`... то есть тут `service_apartments.py` строки
83–107) — но объявление, уже виденное, может встретиться
СРЕДИ круга (не только в конце) из-за ре-ранжирования Крыши между
объявлениями/циклами, что триггерит **преждевременный сброс курсора**
до реального конца выдачи — часть круга проходится повторно, часть
не доходится вовсе за "круг". Это баг детектора конца круга, не
проблема бюджета — **нужно чинить отдельно, до/вместе с внедрением
cold-каталожного сигнала**, иначе <24ч не удержится на практике при
любом бюджете.

**Предложение** (только цифры, без кода): `DEEP_SWEEP_BATCH` 36→**40**
стр/цикл (+4, +11% к ЭТОЙ строке бюджета, компенсируется — см. п.5) →
830/880 ≈ **0.94 суток (22.7 ч)** теоретически, при условии, что
детектор конца круга починен и реально достигает теории (а не 3×
хуже, как сейчас).

## 5. Итоговый бюджет — до/после

| статья | сейчас | предложение | Δ |
|---|---|---|---|
| fresh scan (стр/цикл) | 8 | 8 | 0 |
| deep sweep (стр/цикл) | 36 | **40** | **+4** |
| detail-fetch (обогащение, не архивация) | до 120 (2×60) | без изменений | 0 |
| archive-check (детальных/цикл) | 40, FIFO по `archive_checked_at` | 40, но **приоритет**: hot (score≥90) → cold-каталог-кандидаты на подтверждение → бэклог никогда-не-проверенных | 0 (то же число, другой порядок) |
| **суммарно/сутки к krisha.kz** | ≈1848–4488 | ≈1936–4576 | **+88 (+4 стр × 22 цикла), <5% от суммарного бюджета** |

+4 страницы/цикл — единственный чистый прирост, укладывается в дух
"бюджет ≤ текущего" (не рост порядка величины, не рост параллелизма/
темпа per-request — тот же 2.5–5с политес). Если и это нежелательно —
запасной вариант: срезать `DETAIL_FETCH_BATCH` (обогащение данных,
не архивация) на эквивалентные 4-8 позиций вместо роста deep sweep,
бюджет останется буквально ≤ текущего с точностью до нуля.

## 6. Итог — лаг детекта архива

| пул | размер | механизм | худший лаг |
|---|---|---|---|
| **hot** (score≥90) | 172 (0.4% активных) | детальная проверка, приоритет в archive-check | **≤5.4 ч** (цель 6–12ч ✅) |
| **cold** (остальные) | 37 682 (89.7%) | каталожное отсутствие за полный circle | **≤22.7 ч** теоретически, при условии починки детектора конца круга (сейчас факт — 75.4ч, 3× хуже) |

## 7. Что нужно решить/сделать до кода (следующий проход)

1. **Починить детектор конца круга deep sweep** (п.4) — без этого
   теоретический бюджет не спасёт факт (3× просадка уже есть сегодня).
2. Завести таблицу/поле "видено в текущем каталожном круге" на
   `apartment_listings` (bool/timestamp) — на её основе на завершении
   круга считать diff "было активно → не встретилось" = cold-кандидат
   на detail-подтверждение.
3. Переприоритизировать `check_archived()`: hot (score≥90) первым,
   затем cold-каталожные кандидаты, затем бэклог по старинке (FIFO) —
   реализация текущего запроса `ORDER BY` меняется на композитный
   приоритет, не переписывается с нуля.
4. Определиться, приемлем ли +4 стр/цикл deep sweep, или срезать
   `DETAIL_FETCH_BATCH` взамен (п.5) — решение заказчика, не арифметика.

## 2026-08-13: решение и реализация

Решение заказчика: детектор круга — фикс первым (предусловие). Бюджет
не торгуется — старый равномерный cold detail-fetch (FIFO по всем
активным) срезается целиком, а не расширяется; высвобожденный бюджет —
в каталог (+4 стр/цикл принято). Деталь — только hot-пул +
подтверждения "пропало из выдачи" + новая/изменённая логика. Воркер
один, без параллельности (не менялось — и так был один).

**Реализовано:**

1. **Детектор круга** (`service_apartments.py`) — `max_deep_page`
   раньше пересчитывался КАЖДЫЙ цикл из живого `KRISHA_TOTAL_FOUND`
   (найдена причина 3× просадки: реальный разброс total между
   круг-завершениями в логе — ~830 vs ~1642 страниц за несколько дней,
   движущаяся цель). Теперь снимается ОДИН раз на весь круг
   (`DEEP_SWEEP_CIRCLE_MAX_PAGE` в `app_settings`, обнуляется при
   завершении круга, лениво пересчитывается на первом цикле нового
   круга) — конец круга детерминирован на весь круг вперёд. Заодно
   убран вестигиальный `new_ids`-пречек (36 лишних SELECT/цикл на
   значение, которое фактически не гейтило конец круга — код это
   только логировал, реальный gate был чисто позиционный).
2. **`DEEP_SWEEP_BATCH` 36→40** (`app_settings`, применяется со
   следующего цикла).
3. **`bot/core/archive_check.py` — полный рефакторинг** `check_archived()`:
   старая единая FIFO-очередь по всем активным убрана целиком (не
   расширена). Новая `_select_candidates()` — три приоритетных пула:
   **hot** (`score_total>=90`, ~172 активных, ~0.4%) → **cold_confirm**
   (`last_seen` < начала текущего круга каталога — "пропало из
   выдачи", подтверждение через detail-page) → **backlog** (страховка:
   круга ещё не было, или бюджет остался). `DEEP_SWEEP_CIRCLE_STARTED_AT`
   — новый ключ `app_settings`, порог для cold_confirm.
4. **Метрики** — `parser_cycle_history` получил 4 новые колонки
   (`archive_check_requests`, `archive_hot_checked`,
   `archive_cold_confirm_checked`, `archive_backlog_checked`) —
   archive_check.py раньше вообще не учитывался в "запросы/сутки"
   (свой httpx.AsyncClient, отдельный от apartment_parser/apartment_
   details). Дашборд `/admin/parsers?tab=recheck` — новая секция
   "Adaptive recheck — факт vs цель": hot-лаг медианой (`percentile_cont
   (0.5)` по `now()-archive_checked_at` для score≥90, живой снимок, не
   отдельный лог событий), холодный круг (уже существовавшая метрика,
   переиспользована), запросы/сутки с разбивкой поиск/детали/archive-
   check, разбивка archive-check по пулам за 24ч. Триггер пересмотра
   порога (hot-лаг >12ч медианой) — красная плашка на тайле, не
   автоматический пересчёт (решение — человеку).
5. **Побочная находка**: `apartments.log` дублировал КАЖДУЮ строку
   (millisecond-идентичные пары) — `logging.StreamHandler()` писал в
   stderr, который systemd-юнит уже редиректит в тот же файл
   (`StandardError=append:apartments.log`) — двойной путь в один файл.
   Убран `StreamHandler`, оставлен только `FileHandler`. Тот же паттерн
   (StreamHandler + systemd `StandardOutput/Error=append:` тот же .log),
   вероятно, у других сервисов — не трогал, вне объёма этой задачи.

**Тесты**: `tests/test_archive_check_pools.py` (5 тестов, против живой
БД — hot/cold_confirm/backlog классификация, приоритет по staleness,
уважение лимита через пулы). Полный repo — 141/141.

**НЕ развёрнуто в проде**: `krisha-apartments.service` работает
непрерывно 5+ суток на СТАРОМ коде — изменения требуют перезапуска
сервиса (пере-импорт `service_apartments.py`/`archive_check.py`), не
сделан без явного подтверждения (живой процесс парсинга, не тестовая
среда).
