# Защита исходного ЖК и полного номера дома — 19.10.2026

Статус: код и изолированные проверки, развёртывание не подтверждено.
Миграций, сетевого сбора, перепривязок каталога и исправлений старых строк
этим изменением не выполнено.

## Подтверждённые дефекты

- Геоправило `dedup_listings.find_duplicates` могло признать дублями
  объявления в домах `Туран 6/1` и `Туран 6/2` при одинаковых координатах,
  комнатах, этаже, площади и цене. Общая точка не опровергает разные дома.
- Общий UUID фотографии обходил известные расхождения этажа, комнатности,
  площади и адреса. Повторное использование изображения не исправляет
  эти противоречия.
- `resolve_rental_complex` отвергал известное другое имя ЖК, но принимал
  URL даже при неизвестном имени. Redirect-имя также могло считаться
  подтверждённым написанием без отдельного verified alias.
- `bind_by_address('rental_listings')` заполнял исходный `complex_name`
  каноническим именем по адресу чужих наблюдений продажи. Позднее это
  синтезированное значение могло выглядеть как совпадение с источником.

## Ограниченное новое поведение

`conflicting_house_addresses` проверяет отрицательный факт: одна и та же
распознаваемая улица, но разные полные номера дома/участка, включая дробь
и литеру. Неизвестная улица, разное написание или неполный адрес не дают
нового совпадения либо придуманного алиаса. Нотации участка и дома не
приравниваются. Конфликт исключает пару из всех правил дедупликации,
переназначения primary владельцу и из выбора дома по токену/гео.

Скалярный API `resolve_rental_complex` остаётся совместимым: ID либо None.
Новый `return_decision=True` возвращает `complex_id`, `status`, `reason`,
`source_canonical_id`, `name_canonical_id`. Статусы `unresolved` и `conflict`
всегда имеют `complex_id=None`; результат не записывает ничего в БД.
Ошибка БД пробрасывается и не выдаётся за отрицательное наблюдение источника.

Для разрешения требуются структурный URL и однозначное исходное имя:
собственное имя канонической строки либо явно verified alias. Опция
`resolve_complex_name(..., canonical_names_only=True)` не меняет прежний
режим остальных callers. Зонтик не становится домом: принимаются только
его собственные дети с доказательством `address`/`token`. Несовпадение
исходного имени конкретного ребёнка с найденным другим домом даёт конфликт.

После успешной свежей detail page вызывающий код может использовать
решение для снятия старого FK/постановки на проверку. При сетевой ошибке,
CAPTCHA или нераспознанной странице такое решение применять нельзя.
Интеграция очереди и updater выполняется отдельным изменением; этот helper
сам по себе не очищает старые FK и не подтверждает исчезновение конфликта.

Для аренды адресный `bind_by_address` теперь возвращает ноль до чтения
и записи в БД. Административная ветка продажи оставлена без изменения.
Прямое геозаполнение имени в `service_rental` исправляется владельцем
арендного сборщика отдельно, не этим коммитом.

## Проверки и оставшиеся границы

Изолированные сценарии закрывают соединения с PostgreSQL и используют
placeholder `DATABASE_URL` на `127.0.0.1:1`. Проверка SQL source-spelling
выполнена на приватном SQLite `:memory:`, без PostgreSQL/миграций.
Покрыты полные дроби/литеры, совпадающие координаты, общий UUID изображения,
primary владельца, неизвестные улицы, URL/имя/адрес, неоднозначные aliases,
зонтик и дом, совместимость API и отсутствие синтетического raw имени.

Исторические `complex_name`, уже подменённые каталогом, этим изменением
не восстанавливаются. Нужна новая успешная detail-проверка с сохранением
самостоятельных исходных полей. Старые флаги дублей автоматически не
снимаются; подтверждение физической уникальности требует отдельного аудита.
Геоправило для неизвестных написаний улиц сохранено и не объявлено
доказательством идентичности квартиры. Известный конфликт P1 №81 остаётся
в постоянном карантине до отдельной проверенной корректировки.
