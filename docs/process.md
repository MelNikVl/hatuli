# Процесс: параллельные сессии

Решение заказчика, 2026-08-13.

**Параллельные Claude-сессии над этим репо — только в отдельных git
worktree, никогда в общем рабочем дереве.** Причина: несколько сессий,
пишущих в один и тот же `krisha_bot/` одновременно, гонятся за одними
и теми же файлами (миграции, `app_settings`, скрипты гейтов) — молчаливая
потеря правок одной сессии другой, без конфликта, который было бы видно.
Worktree даёт каждой сессии свою копию файлов при общей истории git.

Существующие worktree сессий — под `.claude/worktrees/` (см. `git worktree
list`), заводятся/чистятся автоматически инструментом сессии (`isolation:
"worktree"` у Agent-тула) либо вручную:

```bash
git worktree add .claude/worktrees/<name> <branch>
```

Не относится к однократным фоновым скриптам/крону (`hype_tracker/
krisha_complex_scan.py` и т.п.) — те не редактируют код репозитория,
только читают/пишут в БД, гонки там другого рода (транзакционные,
не файловые) и вне объёма этого решения.

## Очередь на проверку и конфликты — как обновляется

Таблица «Очередь на проверку и конфликты» на `/admin/entity-ids`
(`complex_source_link_candidates`, `kind IN ('review','conflict')`) —
не снапшот, три независимых источника изменений:

1. **Ручные действия admin'а — в реальном времени.** Подтверждение/
   отклонение кандидата (`approve_candidate`/`reject_candidate`,
   `bot/core/entity_resolution.py`) — прямые синхронные `UPDATE`/
   `DELETE` по клику кнопки на `/admin/entity-ids`, без промежуточного
   кеша: строка исчезает из очереди на следующей перезагрузке страницы
   сразу же, без задержки. Смежные ручные действия по той же модели —
   `set-parent`/`unset-parent` (зонтик/дом, `/admin/umbrellas` и кнопка
   «Сделать ЖК зонтиком» на `/complex/{id}`) — не трогают саму очередь
   кандидатов, но так же применяются немедленно, без фонового шага.
2. **Авто-пополнение парсерами.** Новые кандидаты приходят из
   `score_match()` при очередном матчинге источника с БД ЖК —
   частота появления новых строк равна частоте прогона парсеров
   (krisha/korter/homeportal и т.п.), не отдельному расписанию самой
   очереди.
3. **Рескор при изменениях сигналов уменьшает очередь автоматически**
   (`rescore_review_queue.py`, `rescore_spine_auto.py`) — теперь на
   ежедневном таймере (`krisha-review-rescore.timer`, systemd,
   `OnCalendar=*-*-* 05:30:00` + `RandomizedDelaySec=20m`, задача
   2026-08-13 — раньше запускался только вручную) — когда сигнал, от
   которого зависела неуверенность матча, становится точнее задним
   числом (например адрес-сигнал после бэкфила geo/адреса), повторный
   `score_match()` по уже лежащим в очереди кандидатам может поднять
   уверенность выше порога auto-подтверждения и убрать строку из
   очереди без участия человека. Юнит подхватывается автоматически
   блоком «🕷 Работоспособность парсеров» на `/admin/analytics/overview`
   (динамическое обнаружение всех `krisha-*` systemd-юнитов, см.
   `_krisha_units_status()` в `bot/admin_web.py` — уже был готовый
   список автоматизированных процессов, задача 2026-08-13 "вынеси их
   списком" им и закрылась, без нового кода). См. живой пример (79→66 строк за
   один прогон) в `docs/entity_resolution_plan.md`, раздел «2026-08-13:
   перескор review-очереди».

## Семантика зонтика для источников (Крыша) — задача 2026-08-13

У Крыши нет отдельной карточки под каждый дом расшивленного ЖК —
одна страница `krisha.kz/complex/show/...` представляет комплекс
целиком. Значит связь с источником (`complex_source_links`/legacy
`complexes.krisha_url`) должна жить РОВНО ОДНА, на зонтике, а дома —
только наследовать её для отображения (см. `terminal_extras.py`,
`complex_detail`: фолбэк на `parent_complex_id` в блоке `ext_links`).

**Живой аудит на момент задачи**: из 10 зонтиков 8 уже были корректны
(0 дублей), 2 — нет: #872/#4008 (Rio De Janeiro, дубль через legacy
`krisha_url` — попал туда моей же более ранней правкой этого же дня,
до того как это правило было явно сформулировано) и #1785/#3354
(Qaiyndy, та же legacy-колонка). Оба исправлены прямой правкой данных
(перенос на зонтик, очистка с дома) + 2 связанных стухших review-
кандидата удалены. `#3713 UIA.DARYN` (10 домов) — проверен отдельно,
уже был в правильном состоянии, фикс не потребовался.

**Три уровня защиты от повторного появления дублей**:
1. `krisha_complex_import.py::save_to_db()` — редиректит запись
   `krisha_url` на `parent_complex_id`, если у найденного `complex_id`
   он есть.
2. `hype_tracker/krisha_complex_scan.py` — очередь на обновление
   (`WHERE krisha_url IS NOT NULL`) больше не включает дома
   (`AND parent_complex_id IS NULL`) — не рефрешит дублирующую запись,
   даже если та появится другим путём.
3. `bot/core/entity_resolution.py::record_source_link()` — центральный
   писатель `complex_source_links` (используется всеми score_match-
   пайплайнами: `gap_sweep_krisha_korter.py`, rescore-скриптами и т.п.),
   редиректит `complex_id` на родителя для `source == 'krisha'` ПЕРЕД
   любой записью в спайн/очередь — самый сильный уровень защиты,
   ловит и будущие источники матчинга, не только этот один импортёр.
   Скоуп нарочно ограничен `krisha` — у остальных источников (homeportal
   — своя `matched_complex_id`-схема, korter/homsters — текстовые
   `source_info`) другая природа матчинга, трогать не просили.

**UI `/admin/entity-ids`**: строки с `complex_id` = дом с
`parent_complex_id` теперь не прячутся из очереди (более ранняя версия
этой же задачи их прятала целиком — см. правку выше в этом файле,
теперь отменена), а показываются с подсказкой «⭐ Зонтик: {имя
родителя}» и без кнопок подтвердить/отклонить (заблокировано —
резолвить нужно на зонтике). При живой проверке нашлось ещё
несколько таких строк с других (не krisha) источников — до
`record_source_link()`-редиректа выше (тот скоупнут на krisha) они
по-прежнему могут появляться, UI-подсказка — постоянная защита,
не только переходная мера на время миграции старых данных.

## Deploy-чеклист: «код на диске» ≠ «код в процессе»

Решение заказчика, 2026-08-14 — **третий случай этого класса бага**, по
одному больше не собираем: `krisha-web.service`/долгоживущий процесс
держит модуль в памяти с момента своего старта; правка файла на диске
(включая коммит) сама по себе НЕ доходит до живого запроса — нужен
рестарт. Jinja2-шаблоны частично обманчивы (`.html` перечитывается с
диска на каждый запрос за счёт `auto_reload`), но backend-роут/логика
в `.py` — нет, только рестарт процесса. Первые два случая — см.
докстринг `bot/git_info.py` («adaptive recheck restart-путаница,
повторилась с krisha-web.service на этой же неделе»); третий — правка
аккордеона `/admin/entity-ids` легла на диск в 10:33-10:38, а
`krisha-web.service` не перезапускался с 10:05 — пользователь увидел
старую плоскую вёрстку, хотя коммит (в рабочем дереве) был на месте.

**Чеклист на любую правку `.py`-кода долгоживущего сервиса** (не
относится к разовым скриптам/крону — те стартуют с нуля каждый раз):

1. Коммит с кодом сервиса (или как минимум — правка легла на диск,
   коммит не обязателен для срабатывания бага, обязателен для
   воспроизводимости).
2. Рестарт сервиса: `sudo systemctl restart <unit>.service`.
3. **Проверка, что рестарт реально подхватил новый код** — не
   полагаться на «команда прошла, значит подхватил»:
   - `service_apartments.py`/`service_web.py` — есть готовый механизм
     (`bot/git_info.py::git_hash()`): при старте пишут короткий
     git-хэш в `app_settings` (`APARTMENT_SERVICE_GIT_HASH`/
     `WEB_SERVICE_GIT_HASH`) и в первую строку своего лога
     (`=== ... service started (git=<hash>) ===`). Проверить:
     `grep "service started" apartments.log web.log | tail -2` — хэш
     должен совпадать с `git rev-parse --short HEAD` (или быть новее
     ожидаемого коммита, если правка ещё не закоммичена).
   - Остальные сервисы (rental/geobind/korter/homsters/alerts/sitebot/
     viewcount/market и т.д.) — такого механизма пока нет, проверять
     через `systemctl show <unit> --property=ActiveEnterTimestamp` и
     сверять со временем правки (`stat -c '%y' <файл>`):
     `ActiveEnterTimestamp` должен быть ПОЗЖЕ мтайма правленных файлов.
4. Для страниц — один живой запрос после рестарта (`curl`/браузер),
   не только «сервис активен» — рестарт может пройти успешно, но
   роут — упасть на первом же реальном запросе (нового контекста
   шаблону, опечатки и т.п.), что сам факт `active (running)` не ловит.

**Кандидат на закрытие класса целиком** (не реализовано, только
предложение — при следующей правке `bot/git_info.py` или соседнего
кода): распространить `git_hash()`-паттерн на остальные долгоживущие
сервисы (по аналогии с `service_apartments.py`/`service_web.py`) и
завести один admin-эндпоинт/страницу, сверяющую `app_settings.*_GIT_HASH`
всех сервисов разом с текущим `git rev-parse HEAD` — тогда шаг 3
чеклиста становится одним взглядом на страницу, а не ручным гэп-чеком
по каждому сервису отдельно.
