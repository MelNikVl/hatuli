Статус: **фаза 1 (ЖК) реализована** — см. миграцию
[043_entity_resolution.sql](../migrations/043_entity_resolution.sql),
[bot/core/entity_resolution.py](../bot/core/entity_resolution.py),
интеграцию в [newbuild_common.py](../newbuild_common.py)
`ensure_complex()`, backfill
[backfill_entity_resolution.py](../backfill_entity_resolution.py) и
админ-страницу `/admin/entity-ids` ("АЙДИ"). **Фаза 2 (юниты) — только
план ниже, код не пишется**, пока фаза 1 не покажет уровень шума
авто-матчинга в проде (решение заказчика, 2026-08-12).

## Зачем

Сейчас у каждого источника (Крыша, Korter, Homsters, Homeportal.kz,
застройщики напрямую — BI Group/NAK/ORDA Invest/Bazis/Sensata/Свой дом/
Qadam) — свой ID объекта. Без единого постоянного ID на ЖК все обогащения
(фото, тех.характеристики, отзывы, аналитика) рассыпаны по несвязанным
записям, и нельзя достоверно сказать "это тот же дом".

## Что уже есть (не с нуля)

- `complexes.id` — уже фактически постоянный entity_id ЖК, к нему уже
  пришиты `complex_materials`, `complex_tech_specs`, `complex_reviews`,
  `newbuild_units`, избранное.
- Матчинг сейчас — **по нормализованному имени**: `ensure_complex()`
  ([newbuild_common.py](../newbuild_common.py)) апсертит по
  `lower(name)`; `apartment_listings.complex_name` тоже связывается с
  `complexes.name` через `lower(trim(...))` в SQL-джойнах по всему
  проекту (например [terminal_extras.py](../terminal_extras.py) —
  роут `/admin/complex/{id}`).
- Кросс-связи с источниками — **однослотовые колонки**, не таблица:
  `complexes.krisha_url`, `complexes.korter_url`,
  `complexes.newbuild_source` + `newbuild_source_id` (уникальны как пара,
  но один ЖК = максимум одна связь на источник), плюс
  `complexes.source_info JSONB` — свободный "мусорный ящик" под
  Korter/Homsters обогащение без схемы и без confidence/аудита.
- Ручная правка уже существует: `/admin/analytics/complexes?tab=complexes_fix`
  ([bot/admin_web.py:1080](../bot/admin_web.py)) — переназначение
  объявления на другой ЖК руками. Плюс аудит "мусорных" ЖК/улиц
  ([bot/core/complex_audit.py](../bot/core/complex_audit.py)).

## Слабые места текущей схемы

1. **Матчинг по имени — единственный сигнал.** Опечатка, ребрендинг
   застройщиком, два разных ЖК с одинаковым названием в разных районах —
   молча сливаются или расходятся, без объяснимости "почему".
2. **Один слот на источник.** Если у ЖК окажется два разных ID в одном
   источнике (например, старая и новая карточка на Крыше) — второй
   некуда записать, кроме как затереть первый.
3. **Нет confidence/аудита.** Нельзя посмотреть, когда и почему
   конкретная связь source→complex появилась, и откатить её отдельно от
   остальных.
4. **`source_info` без схемы** — каждый источник пишет туда что хочет,
   читающий код (`complex_detail` в terminal_extras.py) вручную
   разбирает вложенные ключи `korter`/`homsters` руками.

## Решение по ID (зафиксировано, реализовано)

- **PK / entity_id = `complexes.id` (bigint), без семантики.** Никаких
  `jk-nak-001`-подобных ключей с зашитым источником/застройщиком —
  застройщики ребрендятся, ЖК меняют владельцев, транслит плодит дубли.
  Семантика (кто застройщик, откуда пришли) живёт в атрибутах
  (`developer_id`, `complex_source_links.source`), не в ключе.
- **Человеко-читаемый код — отдельная колонка `complexes.code`**, формат
  `JK-000123` (генерируется из id, `bot/core/entity_resolution.generate_complex_code`).
  Мутируема (в теории можно перевыдать), не участвует ни в каком FK —
  чисто для отображения в UI/ссылках, не для связей между таблицами.

## Предлагаемая схема (фаза 1, только ЖК)

Новая таблица-связка, `complexes.id` остаётся единственным entity_id:

```sql
CREATE TABLE complex_source_links (
    id            SERIAL PRIMARY KEY,
    complex_id    INT NOT NULL REFERENCES complexes(id) ON DELETE CASCADE,
    source        TEXT NOT NULL,      -- 'krisha' | 'korter' | 'homsters' |
                                       -- 'homeportal' | 'bi_group' | 'nak' |
                                       -- 'orda_invest' | 'bazis' | 'sensata' |
                                       -- 'svoydom' | 'qadam' | ...
    source_id     TEXT NOT NULL,      -- id/slug объекта в системе источника
    url           TEXT,
    match_method  TEXT NOT NULL,      -- 'name_exact' | 'name_fuzzy+geo' |
                                       -- 'developer_source_id' | 'manual'
    confidence    NUMERIC,            -- 0..1, NULL для manual (=1 по факту)
    matched_at    TIMESTAMPTZ DEFAULT now(),
    matched_by    TEXT,               -- 'auto' | admin username
    UNIQUE (source, source_id)
);
CREATE INDEX ON complex_source_links (complex_id);
```

Один ЖК — много строк (по одной на источник, и даже несколько на один
источник, если понадобится). `complexes.krisha_url`/`korter_url`/
`newbuild_source(_id)`/`source_info` не трогаем сразу — оставляем как
read-through кэш ещё на один цикл, чтобы не ломать существующий код
разом; новые записи пишем в обе схемы, старые колонки выводим из
употребления отдельным шагом после того, как весь читающий код
переедет на `complex_source_links`.

## Матчинг: сигналы и уверенность

Скоринг вместо бинарного да/нет:

- **Точное совпадение нормализованного имени** (текущий метод) — базовый
  сигнал, `confidence` начинается с этого.
- **+ Гео-близость** (координаты источника, если есть, в пределах
  ~150 м от адреса/координат ЖК) — резко поднимает уверенность, ловит
  ребрендинг под новым именем и расходит однофамильцев.
- **+ Застройщик совпадает** (`developers` уже есть как справочник) —
  доп. сигнал.
- **Порог**: выше — авто-связка (`matched_by='auto'`); ниже — попадает в
  очередь на ручную проверку **в существующем UI**
  `/admin/analytics/complexes?tab=complexes_fix` (расширить его, а не
  строить новый инструмент — там уже есть паттерн "показать кандидат →
  подтвердить/отклонить").

## Миграция существующих данных

Разовый backfill-скрипт (в духе уже существующих
`map_csv_db.py`/`match_site_csv.py` в репозитории):
1. Из `complexes.krisha_url`/`korter_url` → строки с `match_method='manual'`
   (то, что уже стоит руками/историческим импортом, считаем подтверждённым).
2. Из `complexes.newbuild_source`+`newbuild_source_id` → строки с тем же
   методом, что использовался при первичном импорте (`ensure_complex`
   сейчас матчит по имени → `match_method='name_exact'`).
3. Из `complexes.source_info` (korter/homsters блоки) → распарсить
   вложенные `url`/`id`, если есть, иначе оставить как есть (эти два
   источника пока могут остаться на старой схеме, если у блоков нет id).

## Фаза 2 (юниты) — зафиксирована в плане, НЕ реализуется сейчас

Решение заказчика (2026-08-12): расписать сейчас, чтобы спайн фазы 1
сразу строился с прицелом на юниты, но не кодить, пока фаза 1 не
покажет уровень шума авто-матчинга в проде.

Тот же паттерн spine, что и у ЖК:

```sql
CREATE TABLE unit_source_links (
    id            SERIAL PRIMARY KEY,
    unit_id       INT NOT NULL REFERENCES newbuild_units(id) ON DELETE CASCADE,
    source        TEXT NOT NULL,
    source_id     TEXT NOT NULL,
    match_method  TEXT NOT NULL,
    confidence    NUMERIC,
    evidence      JSONB,        -- какие сигналы сработали и с каким весом —
                                 -- в отличие от complex_source_links.match_method
                                 -- (короткая строка), тут нужна разборка "что
                                 -- именно совпало", юнитов на порядок больше ЖК
    matched_at    TIMESTAMPTZ DEFAULT now(),
    matched_by    TEXT,
    UNIQUE (source, source_id)
);
```

entity_id = `newbuild_units.id` (тот же принцип: PK без семантики, как у
ЖК). Что в `evidence` и как считается матчинг:

**Блокировка** (сужаем пространство кандидатов до матчинга, иначе
N×M сравнений юнитов внутри ЖК): по `(complex_id, корпус/секция,
комнатность)` — сравниваем только юнитов внутри одного блока.

**Сигналы внутри блока** (скоринг, не бинарно):
- Этаж — высокий вес (точное совпадение почти всегда значит один и тот
  же юнит в пределах блока).
- Метраж — с допуском ±2–3 м² (разные источники округляют по-разному);
  хранить оба значения — «как в источнике» и нормализованное, не
  затирать одно другим.
- Номер квартиры, если парсится из URL/текста источника — почти
  золотой ключ (сразу высокая confidence при совпадении).
- Фингерпринт описания (хэш нормализованного текста) — копипаст между
  площадками при перепубликации одного и того же юнита случается
  часто и это бесплатный сигнал (не нужен внешний API).
- Фото: pHash на каждое фото объявления, пересечение хэшей — сильный
  сигнал; НО фото, встречающееся в 5+ разных объявлениях — считаем
  stock/рендер застройщика и исключаем из матчинга (иначе склеит
  вообще всё с одинаковой обложкой ЖК). Планировка (schematic) —
  стабильнее интерьерных фото, если различима от них — отдельный,
  более надёжный сигнал.
- Вспомогательные (низкий вес поодиночке, но усиливают совпадение):
  цена ±5%, телефон подавшего объявление (если есть в обоих
  источниках), пересечение периодов активности (first_seen/last_seen
  не могут не пересекаться, если это правда один и тот же юнит).

**Пороги** — те же, что в фазе 1 (`AUTO_MATCH_THRESHOLD`/
`REVIEW_QUEUE_THRESHOLD` из `entity_resolution.py`, переиспользуем как
константы, не заводим отдельные). **Review queue** — тот же
существующий UI (`/admin/analytics/complexes?tab=complexes_fix`),
расширить под юниты, а не строить новый инструмент.

## 2026-08-12: сигнал токена очереди/фазы (фикс Darmen-ловушки)

Добавлен сигнал токена очереди/фазы
(`bot.core.entity_resolution._phase_token`, вызывается из `score_match`
через новые опциональные `name_a_full`/`name_b_full` — СЫРЫЕ имена
нужны отдельно от чищенных для trigram, потому что "Дармен (2 очередь)"
после `norm_name()` теряет скобки вместе с номером). Парсит «N-я
очередь», «очередь N», хвостовой номер, хвостовые римские цифры
(валидируются round-trip'ом, отсекает случайные слова вроде "MIX").
Правило: у обеих сторон номер есть и он разный → потолок confidence
`0.79` (не даёт уйти в auto, но не гасит остальные сигналы — решение
просто уходит человеку); равный → небольшой бонус `+0.1`; номер только
с одной стороны → нейтрально, не трогаем.

Три ручных прогона `score_match()` (без БД, с одинаковым гео+
застройщиком, разными именами) подтвердили ровно то поведение, которое
и требовалось:
- `Darmen 2` ↔ `Darmen 1` → **0.79, review** (было 0.80 auto).
- `Darmen 2` ↔ `Darmen (2 очередь)` → **0.98, auto** (номер совпал —
  бонус, а не потеря сигнала из-за скобок).
- `Darmen` ↔ `Darmen 2` → **0.88, auto**, без капа (номер только с
  одной стороны — не мешаем).

Повторная холостая калибровка тех же 60 объектов (те же `object_id`,
не новая случайная выборка) с сигналом фазы: **34 auto / 25 review / 1
skip** — авто просело всего на 1 из 60, и это именно `Darmen 2`↔`Darmen
1` (заслуженно). Два уже-review случая (`MoD.Comfort-1`↔`Mod Comfort-3`,
`Highvill Park-1`↔`Highvill Park 2`) остались review — там cap не бил
(и без него confidence уже был ниже 0.79).

## 2026-08-12: sibling-sweep на живом newbuild-прогоне — второй фикс (implicit phase 1)

Живой прогон `newbuild_weekly.py` (все 5 импортёров, rc=0, 0 ошибок,
612 с) сам по себе не добавил новых spine-записей — реестр не изменился
за несколько часов между автоматическим `Persistent=true` докатом
таймера (машина была выключена в момент понедельничного триггера,
докатился сегодня в 13:55–15:13, ДО этого ручного прогона) и ручным
запуском в 20:30: все 94 ЖК уже были в spine, `ON CONFLICT DO NOTHING`.
Это же и стало досрочной проверкой идемпотентности (п.5 плана) — два
прогона подряд, ноль новых строк, ноль дублей кандидатов
(`UNIQUE(source, source_id, complex_id)` + `DO UPDATE`, не растёт).

Единственная свежая активность — 21 review-кандидат (18 bazis + 3
orda_invest), все на 0.75 (`name_exact+developer`). Причина —
структурная, не шум: `bazis_import.py`/`orda_invest_import.py` вообще
не отдают geo/адрес (`address=None` в коде), поэтому даже 100%-точное
имя не наберёт 0.8 никогда. Топ-10 review 0.7–0.79 (п.3 плана) — ровно
эти записи, все «очевидно те же» ЖК. Конфликтов — 0 за всё время по
всем 5 источникам.

Дальше — sibling-pair sweep (один застройщик, ≤150 м, схожие имена) по
всей базе ЖК новостроек нашёл 7 реальных пар вида «база + номер фазы»
и **6 из 7 всё ещё проходили в auto** несмотря на фикс токена фазы
выше:

```
GAUHARTAS      vs Gauhartas 2      -> 0.91 auto  (WOULD MERGE)
Nur Aspan      vs Nur Aspan 2      -> 0.91 auto  (WOULD MERGE)
Махаббат       vs Махаббат-2       -> 0.90 auto  (WOULD MERGE)
Акерке         vs Акерке-2         -> 0.88 auto  (WOULD MERGE)
Отан           vs Отан 2           -> 0.84 auto  (WOULD MERGE)
Inju Arena     vs Inju Arena 2     -> 0.91 auto  (WOULD MERGE)
Asylym Park 1  vs Asylym Park 2    -> 0.79 review (единственная, где номер
                                       был с ОБЕИХ сторон — только её и
                                       ловило правило "с одной стороны ->
                                       нейтрально")
```

Причина: правило "номер только с одной стороны → нейтрально" (буквально
заданное правило, дало верный результат на синтетическом
`Darmen`↔`Darmen 2` → без капа) не покрывает доминирующий в реальных
данных паттерн — **первую очередь почти никогда не подписывают номером
вовсе** ("Nur Aspan"/"Nur Aspan 2", а не "Nur Aspan 1"/"Nur Aspan 2").
У безномерной стороны токена нет вовсе -> нейтрально -> в auto её
тащат геосигнал+застройщик, ровно как когда-то тащили Darmen.

Подтверждено дополнительно прямо в БД: `Landmark Gold` (id 2451) и
`Landmark Gold, V очередь` (id 4103) — уже отдельные строки
`complexes`; `Поколение Бизнес` (3966) и `Поколение Бизнес 2` (1688) —
тоже отдельные. Т.е. для этих самых застройщиков в базе УЖЕ есть
прецедент "фаза = отдельный complex_id" — auto-слияние безномерной
стороны с номерованной было бы реальной ошибкой, не гипотетической.

**Фикс:** `_phase_token()` теперь возвращает `(номер, база_без_суффикса)`.
Когда номер есть только с одной стороны — сравниваем "голую" сторону с
базой номерованной (той же строкой без суффикса фазы). Совпадают
(similarity >= 0.8) → голая сторона это неявная фаза "1", дальше как
обычно (равно → бонус, не равно → потолок 0.79). Не совпадают →
цифра, похоже, не про фазу вообще — нейтрально, как раньше.

Это меняет результат зафиксированного ранее теста: `Darmen` ↔
`Darmen 2` **больше не "auto без капа"**, теперь `0.79, review`
(`phase_mismatch(1~implicit!=2)`) — сознательное решение после того,
как реальные данные (6 из 7 sibling-пар) показали, что старое правило
пропускало именно этот, самый частый в проде паттерн.

Повторные проверки после второго фикса:
- Все 7/7 sibling-пар из живой базы → **review**, ноль `WOULD MERGE`.
- Холостая калибровка тех же 60 homeportal-объектов: **29 auto / 30
  review / 1 skip** (было 34/25/1 после первого фикса, 35/24/1 совсем
  без фиксов). Просадка авто заметнее (35→29, не 35→34) — но при
  разборе каждая из 6 новых demotions объяснима тем же паттерном
  (явный номер очереди у источника против безномерной "базовой" записи
  в `complexes`, например `ЖК "LANDMARK GOLD" (6 очередь)` →
  `Landmark Gold` — и это ЛЕГИТИМНЫЙ повод для review, не шум: у
  Landmark Gold в базе уже есть отдельная строка под конкретную
  очередь, слияние "по умолчанию" было бы реальной ошибкой того же
  типа, что и Darmen). Ни одной demotion без объяснимой причины.
