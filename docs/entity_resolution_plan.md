## Зачем

Сейчас у каждого источника (Крыша, Korter, Homsters, Homeportal.kz,
застройщики напрямую — BI Group/NAK/ORDA Invest/Bazis/Sensata/Свой дом/
Qadam) — свой ID объекта. Без единого постоянного ID на ЖК все обогащения
(фото, тех.характеристики, отзывы, аналитика) рассыпаны по несвязанным
записям, и нельзя достоверно сказать "это тот же дом".

## Что уже есть (не с нуля)

- `complexes.id` — уже фактически постоянный entity_id ЖК, к нему уже
  пришиты `complex_materials`, `complex_tech_specs`, `complex_reviews`,
  `newbuild_units`, избранное.
- Матчинг сейчас — **по нормализованному имени**: `ensure_complex()`
  ([newbuild_common.py](../newbuild_common.py)) апсертит по
  `lower(name)`; `apartment_listings.complex_name` тоже связывается с
  `complexes.name` через `lower(trim(...))` в SQL-джойнах по всему
  проекту (например [terminal_extras.py](../terminal_extras.py) —
  роут `/admin/complex/{id}`).
- Кросс-связи с источниками — **однослотовые колонки**, не таблица:
  `complexes.krisha_url`, `complexes.korter_url`,
  `complexes.newbuild_source` + `newbuild_source_id` (уникальны как пара,
  но один ЖК = максимум одна связь на источник), плюс
  `complexes.source_info JSONB` — свободный "мусорный ящик" под
  Korter/Homsters обогащение без схемы и без confidence/аудита.
- Ручная правка уже существует: `/admin/analytics/complexes?tab=complexes_fix`
  ([bot/admin_web.py:1080](../bot/admin_web.py)) — переназначение
  объявления на другой ЖК руками. Плюс аудит "мусорных" ЖК/улиц
  ([bot/core/complex_audit.py](../bot/core/complex_audit.py)).

## Слабые места текущей схемы

1. **Матчинг по имени — единственный сигнал.** Опечатка, ребрендинг
   застройщиком, два разных ЖК с одинаковым названием в разных районах —
   молча сливаются или расходятся, без объяснимости "почему".
2. **Один слот на источник.** Если у ЖК окажется два разных ID в одном
   источнике (например, старая и новая карточка на Крыше) — второй
   некуда записать, кроме как затереть первый.
3. **Нет confidence/аудита.** Нельзя посмотреть, когда и почему
   конкретная связь source→complex появилась, и откатить её отдельно от
   остальных.
4. **`source_info` без схемы** — каждый источник пишет туда что хочет,
   читающий код (`complex_detail` в terminal_extras.py) вручную
   разбирает вложенные ключи `korter`/`homsters` руками.

## Решение по ID (зафиксировано, реализовано)

- **PK / entity_id = `complexes.id` (bigint), без семантики.** Никаких
  `jk-nak-001`-подобных ключей с зашитым источником/застройщиком —
  застройщики ребрендятся, ЖК меняют владельцев, транслит плодит дубли.
  Семантика (кто застройщик, откуда пришли) живёт в атрибутах
  (`developer_id`, `complex_source_links.source`), не в ключе.
- **Человеко-читаемый код — отдельная колонка `complexes.code`**, формат
  `JK-000123` (генерируется из id, `bot/core/entity_resolution.generate_complex_code`).
  Мутируема (в теории можно перевыдать), не участвует ни в каком FK —
  чисто для отображения в UI/ссылках, не для связей между таблицами.

## Предлагаемая схема (фаза 1, только ЖК)

Новая таблица-связка, `complexes.id` остаётся единственным entity_id:

```sql
CREATE TABLE complex_source_links (
    id            SERIAL PRIMARY KEY,
    complex_id    INT NOT NULL REFERENCES complexes(id) ON DELETE CASCADE,
    source        TEXT NOT NULL,      -- 'krisha' | 'korter' | 'homsters' |
                                       -- 'homeportal' | 'bi_group' | 'nak' |
                                       -- 'orda_invest' | 'bazis' | 'sensata' |
                                       -- 'svoydom' | 'qadam' | ...
    source_id     TEXT NOT NULL,      -- id/slug объекта в системе источника
    url           TEXT,
    match_method  TEXT NOT NULL,      -- 'name_exact' | 'name_fuzzy+geo' |
                                       -- 'developer_source_id' | 'manual'
    confidence    NUMERIC,            -- 0..1, NULL для manual (=1 по факту)
    matched_at    TIMESTAMPTZ DEFAULT now(),
    matched_by    TEXT,               -- 'auto' | admin username
    UNIQUE (source, source_id)
);
CREATE INDEX ON complex_source_links (complex_id);
```

Один ЖК — много строк (по одной на источник, и даже несколько на один
источник, если понадобится). `complexes.krisha_url`/`korter_url`/
`newbuild_source(_id)`/`source_info` не трогаем сразу — оставляем как
read-through кэш ещё на один цикл, чтобы не ломать существующий код
разом; новые записи пишем в обе схемы, старые колонки выводим из
употребления отдельным шагом после того, как весь читающий код
переедет на `complex_source_links`.

## Матчинг: сигналы и уверенность

Скоринг вместо бинарного да/нет:

- **Точное совпадение нормализованного имени** (текущий метод) — базовый
  сигнал, `confidence` начинается с этого.
- **+ Гео-близость** (координаты источника, если есть, в пределах
  ~150 м от адреса/координат ЖК) — резко поднимает уверенность, ловит
  ребрендинг под новым именем и расходит однофамильцев.
- **+ Застройщик совпадает** (`developers` уже есть как справочник) —
  доп. сигнал.
- **Порог**: выше — авто-связка (`matched_by='auto'`); ниже — попадает в
  очередь на ручную проверку **в существующем UI**
  `/admin/analytics/complexes?tab=complexes_fix` (расширить его, а не
  строить новый инструмент — там уже есть паттерн "показать кандидат →
  подтвердить/отклонить").

## Миграция существующих данных

Разовый backfill-скрипт (в духе уже существующих
`map_csv_db.py`/`match_site_csv.py` в репозитории):
1. Из `complexes.krisha_url`/`korter_url` → строки с `match_method='manual'`
   (то, что уже стоит руками/историческим импортом, считаем подтверждённым).
2. Из `complexes.newbuild_source`+`newbuild_source_id` → строки с тем же
   методом, что использовался при первичном импорте (`ensure_complex`
   сейчас матчит по имени → `match_method='name_exact'`).
3. Из `complexes.source_info` (korter/homsters блоки) → распарсить
   вложенные `url`/`id`, если есть, иначе оставить как есть (эти два
   источника пока могут остаться на старой схеме, если у блоков нет id).

## Фаза 2 (юниты) — зафиксирована в плане, НЕ реализуется сейчас

Решение заказчика (2026-08-12): расписать сейчас, чтобы спайн фазы 1
сразу строился с прицелом на юниты, но не кодить, пока фаза 1 не
покажет уровень шума авто-матчинга в проде.

Тот же паттерн spine, что и у ЖК:

```sql
CREATE TABLE unit_source_links (
    id            SERIAL PRIMARY KEY,
    unit_id       INT NOT NULL REFERENCES newbuild_units(id) ON DELETE CASCADE,
    source        TEXT NOT NULL,
    source_id     TEXT NOT NULL,
    match_method  TEXT NOT NULL,
    confidence    NUMERIC,
    evidence      JSONB,        -- какие сигналы сработали и с каким весом —
                                 -- в отличие от complex_source_links.match_method
                                 -- (короткая строка), тут нужна разборка "что
                                 -- именно совпало", юнитов на порядок больше ЖК
    matched_at    TIMESTAMPTZ DEFAULT now(),
    matched_by    TEXT,
    UNIQUE (source, source_id)
);
```

entity_id = `newbuild_units.id` (тот же принцип: PK без семантики, как у
ЖК). Что в `evidence` и как считается матчинг:

**Блокировка** (сужаем пространство кандидатов до матчинга, иначе
N×M сравнений юнитов внутри ЖК): по `(complex_id, корпус/секция,
комнатность)` — сравниваем только юнитов внутри одного блока.

**Сигналы внутри блока** (скоринг, не бинарно):
- Этаж — высокий вес (точное совпадение почти всегда значит один и тот
  же юнит в пределах блока).
- Метраж — с допуском ±2–3 м² (разные источники округляют по-разному);
  хранить оба значения — «как в источнике» и нормализованное, не
  затирать одно другим.
- Номер квартиры, если парсится из URL/текста источника — почти
  золотой ключ (сразу высокая confidence при совпадении).
- Фингерпринт описания (хэш нормализованного текста) — копипаст между
  площадками при перепубликации одного и того же юнита случается
  часто и это бесплатный сигнал (не нужен внешний API).
- Фото: pHash на каждое фото объявления, пересечение хэшей — сильный
  сигнал; НО фото, встречающееся в 5+ разных объявлениях — считаем
  stock/рендер застройщика и исключаем из матчинга (иначе склеит
  вообще всё с одинаковой обложкой ЖК). Планировка (schematic) —
  стабильнее интерьерных фото, если различима от них — отдельный,
  более надёжный сигнал.
- Вспомогательные (низкий вес поодиночке, но усиливают совпадение):
  цена ±5%, телефон подавшего объявление (если есть в обоих
  источниках), пересечение периодов активности (first_seen/last_seen
  не могут не пересекаться, если это правда один и тот же юнит).

**Пороги** — те же, что в фазе 1 (`AUTO_MATCH_THRESHOLD`/
`REVIEW_QUEUE_THRESHOLD` из `entity_resolution.py`, переиспользуем как
константы, не заводим отдельные). **Review queue** — тот же
существующий UI (`/admin/analytics/complexes?tab=complexes_fix`),
расширить под юниты, а не строить новый инструмент.

## 2026-08-13: Фаза 2 — методология по итогам фазы 1 (гейт условие проверено)

Условие запуска фазы 2 (см. выше) — "план расписан, код не пишется,
пока фаза 1 не покажет уровень шума авто-матчинга в проде". Фаза 1
отработала в проде весь день 2026-08-12/13 (spine, гейт-мердж, review-UX,
adaptive recheck) — условие проверяемо, не гипотетически.

### Что фаза 1 реально показала про "уровень шума"

Не абстрактно — конкретные числа из живых прогонов:
- **Наивный OR-критерий (гео/developer/address) без перекрёстных
  проверок — ~25%+ реальных ошибок на первых же кейсах.** Гейт-10
  транслит-мерджа поймал 1 живую ошибку из 10 (10%) сразу, а по итогам
  полного разбора — 5 отдельных классов багов (phase-conflict без
  транслита, двухходовая split-lineage, отсутствие словаря-синонима
  "позиция", неограниченный developer-mismatch, непереименованный
  после расшивки паспорт), каждый нашёлся ТОЛЬКО через ручной спот-чек
  реальных результатов, не через код-ревью заранее.
- **После итеративных гвардов (5 предохранителей) — 0 ошибок на 120
  мерджах**, подтверждено спот-чеком 10 случайных пар + assert
  "unravel_involved не тронут" + повторный sweep (199→91 групп, все
  26 оставшихся "высокая уверенность по гео" объяснены явной причиной).
- **Гипотезы о структуре сигнала регулярно опровергались фактом**, не
  подтверждались: "hot=новое объявление" (58% архиваций у объявлений
  старше 14 дней, не у свежих), "первая очередь = без номера везде"
  (implicit-phase-1 понадобился отдельным фиксом), "адрес всегда
  доступен" (address_match не сработал НИ РАЗУ на 54 krisha spine-
  строках — `complexes.address` пуст структурно).

**Вывод методологии**: сигналы для фазы 2 нельзя спроектировать
заранее и один раз откалибровать — план ниже (веса/пороги) это
ГИПОТЕЗА для первого гейта, не финальная конфигурация. Дисциплина
фазы 1 (гейт 10 → спот-чек → массово; provenance-lineage предохранитель;
review-UX ДО массовых решений, не после) переносится в фазу 2 как
обязательная, не опциональная практика.

### Гейт перед гейтом: данные для матчинга физически не там, где ожидалось

Проверил по факту (не по плану) — где вообще есть overlap для матчинга
юнитов:

| источник | юнитов | ЖК | фото |
|---|---|---|---|
| bi_group | 7988 | 58 | 0 |
| sensata | 1959 | 11 | 0 |
| bazis | 1548 | 18 | 0 |
| svoydom | 1318 | 14 | 0 |
| nak | 262 | 2 | 0 |
| orda_invest | 39 | 3 | 0 |

**Комплексов с юнитами от 2+ источников (newbuild_units × newbuild_units)
— 0.** Каждый источник покрывает СВОИ ЖК, пересечения между
developer-прямыми источниками нет вовсе — план фазы 2 (сравнение
`unit_source_links` между source'ами newbuild_units) сегодня решал бы
задачу с НУЛЕВЫМ количеством реальных пар. Фото — 0 у ВСЕХ источников
(`photos` пуст) — pHash-сигнал из плана нереализуем без отдельного
сбора фото, которого сейчас нет вообще.

**Реальный overlap — в другом месте**: `apartment_listings` (обычные
объявления Крыши от физлиц/риелторов, часто перепродающих застройщика)
с `is_new_build=TRUE` — 363 строки, из них **29 ЖК** пересекаются с
`newbuild_units` по `complex_id` (через `complexes.name`). Это и есть
настоящая задача дедупликации юнитов — "то же самое жильё, что
застройщик продаёт напрямую (newbuild_units) и что переоформлено на
Крыше от риелтора (apartment_listings)" — не "три застройщика продают
один ЖК" (такого не бывает структурно).

### Пересмотр плана под факт

1. **Блокировка** остаётся `(complex_id, комнатность)` — но сравниваем
   `newbuild_units` (сторона застройщика) против `apartment_listings
   WHERE is_new_build=TRUE` (сторона Крыши), не units×units.
   `building`/`section` есть только у стороны застройщика — Крыша
   такого не парсит, сигнал одноsторонний, участвует только когда
   доступен с обеих сторон (тот же принцип, что address_match).
2. **Фото/pHash — не в первый гейт.** Нет данных вовсе (0 фото у
   newbuild_units), а собирать их специально под гипотетический сигнал
   — работа отдельного масштаба (обход фото застройщиков), не часть
   алгоритма матчинга. Отложено, не отменено — тот же паттерн, что
   address-backfill для фазы 1 (голодающий сигнал — сначала данные,
   потом вес).
3. **Первый гейт — те же 29 ЖК, не вся база.** Малый, проверяемый
   вручную набор (десятки-сотни юнитов, не тысячи) — гейт 10 →
   спот-чек → массово по ТОЙ ЖЕ дисциплине, что транслит-мердж.
   Signals для первого прохода: этаж (точное совпадение), метраж
   (±2-3м²), цена (±5%), пересечение first_seen/last_seen — все
   уже собираются, ничего нового не нужно тянуть с источников.
4. **`unit_duplicate_candidates`, не `unit_source_links` для review** —
   тот же паттерн, что `complex_duplicate_candidates` (эта задача —
   дубль СУЩНОСТИ между источниками одного типа данных, не привязка
   "источник→ЖК"), review-UX по тому же шаблону (evidence инлайн,
   bulk-eligible фильтр) сразу, не после первого прогона.
5. **provenance-lineage предохранитель заранее**, не постфактум — если
   юнит когда-либо разбирался вручную (одобрен/отклонён в review), это
   должно блокировать повторное авто-решение так же, как
   `unravel_involved_ids()` блокирует транслит-мердж для тронутых
   расшивкой id.

### Numbers-first проход — реальные 28 ЖК, до кода

(Уточнение: комплексов с overlap реально 28, не 29 — округление в
предыдущем проходе.) Блокировка `(complex_id, комнатность)` между
`newbuild_units` (застройщик) и `apartment_listings WHERE is_new_build`
(Крыша) на всех 28 ЖК:

| шаг | пар | % от блокировки |
|---|---|---|
| блокировка (complex_id, комнатность) | **1710** | 100% |
| + этаж точное совпадение | 151 | 8.8% |
| + метраж ±3м² (оба сигнала) | **75** | 4.4% |
| + цена ±5% (доп. к этажу+метражу) | 32 | 1.9% (42.7% от 75) |
| + пересечение first_seen/last_seen (доп. к этажу+метражу) | 26 | 1.5% (34.7% от 75) |
| этаж+метраж, подтверждено ЦЕНОЙ ИЛИ ДАТОЙ | 45 | 2.6% (**60%** от 75) |
| этаж+метраж, **БЕЗ подтверждения ни одним** | **30** | 1.8% (**40%** от 75) |

**Вывод**: этаж+метраж сам по себе даёт правдоподобный кандидат-пул
(75 из 1710, 95.6% отсева блокировки) — но **40% этих кандидатов (30
пар) не подтверждаются ни ценой, ни пересечением дат активности вовсе**.
Дома с повторяющейся планировкой (тот же этаж, та же площадь на разных
секциях/подъездах) — реальный источник ложных совпадений именно на
этой паре сигналов, тот же класс риска, что naive OR-критерий в
транслит-мердже фазы 1 (sibling-sweep урок: geo+developer одни, без
перекрёстной проверки, дали 6/7 ложных auto). Цена/дата не опциональные
"вспомогательные" сигналы из исходного плана — они закрывают
структурную дыру, которую этаж+метраж не закрывают сами.

**Решение для первого гейта фазы 2** (когда до него дойдёт): auto —
этаж+метраж И (цена ИЛИ дата), то есть ровно тот 60%-ный "45" —
остальные 30 (этаж+метраж без подтверждения) — в review
(`unit_duplicate_candidates`), не auto и не молчаливый пропуск. Ни
одного пропущенного нб/al без пары данных (price_missing=0 на этой
выборке) — в отличие от фазы 1, здесь цена доступна с обеих сторон
всегда, сигнал не голодает.

## 2026-08-12: политика гранулярности ЖК (расшивка blob-комплексов)

Найдено при разборке blob-аудита: адресное расхождение между точками
одного `complex_id` — не всегда ошибка матчинга. Многие крупные
проекты (`Городской Романс`, `AUSTRIA`, `Millennium Park`, ...) имеют
по многу пятен/кварталов строительных разрешений с формально разными
привязками к улице — это ОДИН проект, просто административно нарезан
на участки. Настоящая ошибка — Family Nest A/B/F, UIA.BIRLIK A-E — где
источник сам явно и однозначно называет каждую часть отдельным именем
(буква/номер блока или очереди), это разные маркетинговые сущности.

**Правило:** комплекс = проект одного permit-ареала (одна стройка,
один застройщик, один этап согласования, даже если формально несколько
участков/пятен). Отдельный `complex_id` — только когда источник сам
явно и однозначно нумерует/литерует части (очередь/блок/корпус с
единичным явным значением на КАЖДОЙ сравниваемой стороне). "Пятно N"/
"квартал N" (пермитная нарезка участка, не маркетинговая единица) и
перечисления номеров ("блоки 1, 2, 3", "пятна 6, 9" — про диапазон, не
про конкретный блок) — никогда не повод для разделения, весь диапазон
остаётся одним ЖК.

### Правила кластеризации для расшивки

1. Явный токен фазы/блока с ОБЕИХ сторон, разный → **split** (разные
   complex_id).
2. Токен явный только с одной стороны, "голая" база совпадает с базой
   номерованной (implicit phase 1, см. `_phase_token`/`score_match`) →
   **split** — тот же принцип, что и у самого сигнала фазы в score_match.
3. "Пятно N"/"квартал N"/перечисление номеров ("1, 2, 3") → **никогда
   не split**, весь диапазон один ЖК (`_phase_token` теперь явно
   возвращает `None` для этих случаев, см. `_PYATNO_KVARTAL_RE`/
   `_ENUM_LIST_RE`).
4. Без явных токенов вовсе, но доверенные (не закарантиненные) адреса
   расходятся И реальное гео > 1 км → **review**, не автоматическое
   решение — человек смотрит руками.

## 2026-08-13: расшивка как review-очередь (второй источник сигнала)

Решение заказчика: правила кластеризации выше (1-4) остаются
неизменными — новое здесь ТОЛЬКО источник сигнала и то, что решение
теперь идёт через UI-очередь (`split_candidates`,
`migrations/053_split_candidates.sql`), а не разовый скрипт-прогон.

**Два источника, одна политика:**
- `unravel_blobs.py` (2026-08-12) — homeportal_objects, явный токен
  В ИМЕНИ homeportal-объекта, кластеризация по `address_match()`,
  исполняет сразу (auto-split с review-router для "мега"-случаев).
- `split_detect.py` (сегодня) — apartment_listings (Крыша) ВНУТРИ
  одного `complex_id`: гео-кластеризация объявлений (>1км друг от
  друга — тот же порог, что правило 4) + явный маркер очереди/блока/
  литеры **в title/description конкретного объявления** (не в имени
  ЖК — там для этого уже есть `_phase_token`). Пишет ТОЛЬКО в очередь
  (`split_candidates`, `status='review'`), не исполняет сам — задача
  явно требует накопления gold labels перед доверием.

**Почему не парсить "Расположение"/"Срок сдачи" со страницы ЖК
Крыши как источник кластеров.** Первая идея — расширить
`krisha_complex_import.py` пер-очередными адресами прямо со страницы
ЖК. Живая проверка (Rio de Janeiro, см. кейс ниже) показала: страница
отдаёт ОДНУ строку адреса на весь ЖК ("ул. Бейбарыс Султан, 23, 25,
25/2, 25/3, 25/4, 27") без привязки конкретного дома к конкретной
очереди, и ОДНУ строку срока сдачи с очередями через точку ("Первая
очередь - IV квартал 2020 г. Вторая очередь - ..."). Сопоставить
"очередь N" конкретному дому из адресной строки нельзя надёжно —
порядок домов в адресе не гарантированно совпадает с порядком очередей
в сроке сдачи. `krisha_complex_import.py` теперь парсит срок сдачи в
`source_info->krisha.deadlines_by_queue` (список `{label, deadline}`)
как ОБОГАЩЕНИЕ (полезно человеку читать), но это НЕ сигнал для
`split_detect.py` — сигнал берётся с апартамент-listing уровня, где
координаты/текст у каждого объявления свои.

**Правила отнесения (`build_evidence()` в `split_detect.py`):**
2+ гео-кластера (порог правила 4, >1км) размером ≥2 объявления каждый,
крупнейший — паспорт (не создаёт нового complex_id, тот же принцип,
что canon в транслит-мердже — "кто больше, тот остаётся"). У КАЖДОГО
не-паспортного кластера есть явный маркер (хотя бы одно объявление) →
`explicit_token_address` (это и есть правило 1/2, применённое на новом
источнике). Хотя бы у одного не-паспортного кластера маркера нет →
`address_diverge_no_token` — правило 4, "решает человек", тот же
случай, что AUSTRIA в таблице вердиктов: адрес один не решает.

**Пометка руками** (`flag_split_candidate`, кнопка на
`/admin/entity-ids` и на карточке ЖК `/complex/{id}`) — человек видит
что-то подозрительное (не обязательно то, что нашёл бы детектор),
пишет комментарий, candidate уходит в ту же очередь с `reason='manual'`
и пустым `evidence` — подтверждение такой пометки только фиксирует
статус, реальное разнесение (если оно вообще нужно) человек делает
руками отдельно, playbook (`_execute_split_cluster`) действует только
там, где evidence содержит структурированные кластеры.

**Playbook исполнения** (`approve_split_candidate` →
`_execute_split_cluster`, `bot/core/entity_resolution.py`):
`apartment_listings` привязаны к `complexes` ИМЕНЕМ (`lower/trim`), не
FK — в отличие от `unravel_blobs.py` (тот руками переносит
`complex_source_links`), тут для большинства кейсов исполнение — это
просто создание строки `complexes` с именем дочернего кластера, дальше
уже существующие объявления сами приджойнятся по имени. Если такая
строка УЖЕ существует (живой кейс Rio De Janeiro 3 ниже) — не
дублируем, только доливаем `provenance` (`split_from`/
`matched_by='unravel'` — тот же формат, что `unravel_blobs.py`, оба
пути расшивки неотличимы по provenance постфактум).

**Гейт авто-исполнения** (`split_auto_execution_allowed`, решение
заказчика): явное правило (`explicit_token_address`, тот же
застройщик по обе стороны — застройщик как доп. фильтр ещё предстоит
добавить в `split_detect.py`, сейчас гейт общий на reason-корзину) —
доверять без человека можно ТОЛЬКО после **10 решённых вручную
(approve+reject) с точностью approved/decided ≥95%** на этой
reason-корзине. 0 решений на 2026-08-13 → гейт всегда `False`, весь
вывод `split_detect.py` идёт в review — режим накопления, тот же
принцип, что gold labels у Фазы 2 (юниты).

**Живой прогон `split_detect.py --test`** (2026-08-13, 2017 ЖК без
предыдущих `split_candidates`, ≥4 объявления с координатами каждый):
**3 кандидата**, все `address_diverge_no_token` (0
`explicit_token_address` — узкий, высокоточный сигнал, ожидаемо не
сработал ни разу на первом проходе). Гео-кластеризация — простой
порог >1км (union-find), без семантики `address_match()` (та сравнивает
токены улицы, эта — сырую дистанцию) — заведомо шумнее, отсюда и
осторожная категория `address_diverge_no_token` для всех живых
находок: часть могут быть просто протяжённые кварталы на одной улице
(см. "Авиценна" — оба кластера на ул. Мангилик Ел), не настоящий блоб;
решает человек через очередь, автоматика не рискует.

## 2026-08-13: расшивка — многоуровневый детектор (второй проход)

Решение заказчика: `split_detect.py` собирает evidence из НЕСКОЛЬКИХ
источников разом на каждый `complex_id`, не только из

одну проекцию. Правила кластеризации (granularity policy, см. выше)
не меняются — меняется только откуда берутся данные и как их теперь

**Источники и живая проверка структуры (обязательный шаг ДО парсинга

| метрика | запрос | значение |
|---|---|---|

**56 vs 52 — гипотеза из задачи ("4 INSERT из упавшей попытки до фикса
[object_id]") НЕ подтвердилась и неверна по конструкции**: PostgreSQL
откатывает INSERT целиком при нарушении unique constraint — упавшая
попытка физически не может оставить в таблице частичную/висячую
строку, а сам код (`unravel_blobs.py`) ловит именно это исключение и
тут же делает ВТОРОЙ, успешный INSERT с дизамбигуированным именем — то
есть на каждую коллизию всё равно ровно 1 финальная строка, не 2 и не
0. **Реальная причина** — прямо в логе: 4 родителя в пасс1 разошлись
не на 1, а на **2 новых кластера каждый** (`SPLIT auto (2 новых
кластеров)`: `#1866 Altyn Saulet`, `#2094 Besterek`, + 2 других) — 46
родителей × 1 кластер + 4 родителя × 2 кластера = 54 строки в пасс1,
+ 2 в пасс2 = 56, при 52 паспортах. Чистая арифметика "1 паспорт = 1
новый complex" была неверным допущением задачи, не багом кода.

## 2026-08-13: модель зонтик/дом (parent_complex_id)

Решение заказчика: `complexes.parent_complex_id` (nullable, self-FK,
`migrations/054_parent_complex_id.sql`) — структурная, ВСЕГДА-текущая
принадлежность "дом -> зонтик". Отдельно от `provenance.split_from`
(JSONB, история происхождения, не переписывается задним числом) —
обычная колонка, не JSONB, нужна для JOIN на публичных страницах
(список домов зонтика, "часть комплекса X" на странице дома) и в
админке, а не только для чтения истории постфактум.

**Автоматически** — `_execute_split_cluster`/`_execute_split_
homeportal_blocks` (`bot/core/entity_resolution.py`) теперь ставят
`parent_complex_id = COALESCE(parent_complex_id, <паспорт>)` на
child при КАЖДОЙ расшивке (не перезаписывают, если у existing-строки
уже свой родитель — например, после umbrella-кейса ниже, где родитель
переставляется вручную на настоящий зонтик, а не паспорт-блок).

**Вручную** — `set_parent_complex()` — кнопка "🏠 Добавить дом к ЖК"
на каждой строке очереди расшивки и на карточке любого ЖК. Защиты:
нельзя назначить себя родителем, нельзя создать цикл (проверка вверх
по цепочке).

### Политика источников блочной структуры (зафиксировано по факту)

| источник | роль |
|---|---|
| **Homeportal** (`apartment_data[].spot_number` + адрес/гео per-объект) | **Первичный.** Уже в БД, ничего не фетчит — реальные пер-блочные записи, каждая своим `object_id`, каждый с собственным адресом/гео. Единственный источник, реально дающий структуру, а не одну строку на весь ЖК. |
| **Крыша** (`deadlines_by_queue`) | **Вспомогательный.** Даёт срок сдачи по очередям (обогащение), но НЕ адрес по очередям (одна строка на весь ЖК, см. запись выше "расшивка как review-очередь") — не самостоятельный сигнал структуры, только контекст при ручном решении. |
| **Korter / Homsters** | **Ноль.** Живая проверка (см. таблицу выше в этом файле) — обе площадки отдают одну запись на весь ЖК структурно, пер-блочных данных нет вовсе. |
