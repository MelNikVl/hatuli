  `ON CONFLICT DO NOTHING` сохраняет первое наблюдение дня; повторное сканирование

  распределения по срезам: изменение цены 20→30 тыс. внутри дня сохраняет
  первый снимок 20 тыс., но даёт в индексе 30 тыс. и n=1. Обычный `last_seen`
  или обогащение описания такое подтверждение не заменяют.
- Описание берётся из уже запрошенной детальной страницы. Число запросов,
  batch, паузы и временной бюджет не увеличены. Пустое описание отмечается как
  проверенное; изменившиеся правила мебели применяются к сохранённому тексту
  без нового HTTP-запроса и без обновления `last_seen`.
- Месячный и stage-2 rebuild используют одну транзакцию. Ошибка нового
  построения откатывает и месячный rebuild. Daily/furnished cleanup затрагивает
  только собственные apartment/Astana-срезы, исходные наблюдения не удаляет.

## Единицы, окна и происхождение

| Данные | Правило |
| --- | --- |
| Месячные цены | Только `monthly`, свежие активные недублированные источники ≤72 часов; базовый policy `3` сохранён |
| Посуточные цены | Реальные `daily`-снимки с `period_source_checked` и более поздние подтверждённые наблюдения текущего каталожного эпизода; сначала 30 дней, при нехватке n — 90 |
| Подсчёт n | Один последний снимок на отдельный исходный ID в выбранном окне, а не число обходов или снимков |
| Порог | ЖК ≥5, район/город ≥10, гекс ≥5; настройки не опускают эти минимумы |
| Активное предложение | Отдельный счётчик актуальных активных источников ≤72 часов в том же срезе, периоде и сетке |
| Допуск индекса | Достаточный n, активное предложение >0, корректные P25/медиана/P75, дата обновления и последнее реальное наблюдение ≤72 часов |
| История 90 дней | Самое старое наблюдение может быть внутри 90-дневного окна; это явно подписанное распределение сохранённых цен предложений, не утверждение об актуальности каждой старой квартиры |
| Идентичность ЖК | Повторно используются строгие canonical/source/name-гейты этапа 0; зонтик, угадывание по расстоянию или конфликт имени не создают точный ЖК-срез |
| Гекс | Ключ включает `hex_edge_m`, ID гекса, точные комнаты, период и мебель; разные размеры сетки не смешиваются |

До рабочей миграции 112 прошлых снимков этого контура нет. Первая подтверждённая
daily-страница этапа 0 — 20 карточек в 23:25:57 UTC+5 — не превращается
этой миграцией в прошлую историю. Синтетический backfill из `last_seen`, ценовой
эвристики или сегодняшнего снимка не предусмотрен. Фактическое покрытие
район × комнаты после 112 ещё не измерено; готовые 30/90 дней не обещаются.

На вкладке показываются только прошедшие гейт показатели. При малом n
пустые гексы не закрашиваются, нет готовой пары — нет отношения цен. У каждой
готовой цены есть единица ₸/мес или ₸/сут, P25/P75, n, окно и время источника.
Отношение «сутки / месяц» — арифметика двух цен, без заявления о загрузке,
выручке или доходности. Счётчик объявлений не обозначает спрос и не доказывает
полноту рынка.

## Подтверждённое снятие с источника

Для месячных объявлений считается интервал **от первого реально сохранённого
monthly-снимка текущего доказанного эпизода до `archived_at`**, у подтверждённых
снятий за последние 30 дней. Старый `found_at` не доказывает месячную аренду:
у legacy-ID от августа период мог впервые подтвердиться только сегодня.
Неизвестный→известный период, реактивация или перерыв успешных наблюдений
выдачи более 72 часов начинают новый эпизод. Это происходит атомарно в upsert;
обогащение описания не меняет эпизод и не создаёт свежесть.

Нужны минимум два разных дня immutable-подтверждений именно этого эпизода,
интервал не менее двух суток и последнее такое подтверждение не старше
72 часов к снятию. Если реактивация произошла в тот же UTC-день, первый
снимок дня не переписывается: новый эпизод консервативно ждёт следующих
снимков, доказательства предыдущего не заимствует. Старые архивы без ledger,
неизвестный исторический период и недоказанные разрывы исключены.
Принимаются только
`archived_badge`/`confirmed_gone`; исключены дубли/спорные дубли, конфликты периода,
интервалы менее двух дней и `sweep_stale`. Медиана публикуется только при
достаточном n снятий (те же минимумы 5/10).

В интерфейсе это **«до снятия с источника»**, а не «сдаётся за N дней».
Фактическая сдача, дата договора, занятость и спрос неизвестны. Поле
`months_of_supply` хранит лишь отношение свежего активного предложения к числу
наблюдавшихся подтверждённых снятий за 30 дней; оно не выдаётся за срок
поглощения реальными арендаторами. Формулы vacancy/net yield/Deal Score этим
этапом не менялись. Из снятий не выводится вакантность.

## Мебель и внешняя приёмка

Классификатор `rental_furnishing.py` возвращает `none/partial/full/unknown` по
явным текстовым сигналам. «С мебелью», хороший ремонт или один диван сами по
себе не означают полную меблировку. Противоречивые сигналы/отрицания дают
`unknown`. Ограниченные пользовательские regex читаются из
`RENTAL_FURNISHING_RULES_JSON`; опасные/некорректные выражения не выполняются.
Версия включает SHA базовых и дополнительных правил.

**Точность на 50 реальных объявлениях не измерена. Внешняя валидация ожидается.**
Синтетические unit-кейсы проверяют только поведение кода. Они не являются
разметкой рынка, даже если их больше 50.

Подготовлен offline-процесс без БД и HTTP:

```bash
python scripts/audit_rental_furnishing.py --template --output /private/rental-audit/dataset.json
```

Оператор отдельно открывает минимум 50 различных настоящих Krisha-источников,
сохраняет разные скриншоты приватно и независимо размечает мебель до просмотра
ответа классификатора (`label_source=human_blind`). Схема содержит URL/ID,
время проверки, наблюдённый title/description и SHA текста, label/reviewer,
относительный путь и SHA браузерного скриншота. Контакты в отчёт не копируются.
Сам набор и изображения остаются вне Git/публичных каталогов.

```bash
python scripts/audit_rental_furnishing.py --input /private/rental-audit/dataset.json \
  --expected-dataset-sha REVIEWED_FULL_SHA256 --output /private/rental-audit/report.json
```

Повторные ID/скриншоты, отсутствие файлов и хешей, неподходящий URL/время
проверки отбраковываются. Отчёт содержит confusion matrix и accuracy. Внутренний
стартовый критерий допуска — ≥50 отдельных проверенных источников, ≥5 примеров
каждой известной категории и accuracy ≥90%, без ошибок доказательств. Это
заранее выбранный гейт, а не измеренный результат или гарантия качества.

CLI не включает настройки. Даже подходящий отчёт требует проверки оператором
и отдельного явного включения `RENTAL_FURNISHING_INDEX_ENABLED=1` с receipt в
`RENTAL_FURNISHING_VALIDATION_RECEIPT`. По умолчанию выключено. Reader проверяет
также версию правил в самой строке индекса; новая receipt не открывает старый
индекс до rebuild. До приёмки furnished-группы не публикуются.
При отсутствии подходящего furnished daily допускается общий daily с честной
меткой `furnishing=None`; full monthly для mid-term не подменяется общим индексом.

## Контракт для этапа 3

Модуль `bot.core.rental_stage2_index`:

- `lookup_daily_rental_estimate(city,district,complex_name,rooms,*,complex_id=None,furnishing=None,allow_city=False)`;
- `lookup_furnished_monthly_estimate(...,furnishing='full',allow_city=False)`;
- `lookup_hex_rental_estimate(hex_id,rooms,*,rent_period='daily',hex_edge_m=None,furnishing=None)`.

Комнаты всегда точные 1–6; без отдельного разрешения нет city fallback.
Daily policy `daily_v1`, full-monthly `furnished_monthly_v1`, monthly-hex
`hex_monthly_v1`. Возвращаются цены/P25/P75, n, active_supply, окно, даты
источника/индекса и уровень (`ЖК`, `район`, `город`, `гекс`). До 112 или без
готовых данных возвращается `None`. Мебель требует общего гейта
`furnishing_index_row_ready(row, settings)`.
