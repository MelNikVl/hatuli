# Единая темпоральная политика

Решение заказчика, 2026-08-14, по итогам [`data_collection_audit.md`](data_collection_audit.md)
(§4, гэп-репорт). Это не ретроспективный документ — правило для НОВЫХ
таблиц/полей начиная с этой даты; существующие гэпы закрываются по
очереди отдельными задачами (Г12/Г2/Г3 — приоритет 1, сделаны
2026-08-14, см. [`scoring_roadmap.md`](scoring_roadmap.md) и коммиты
`Г12:`/`Г2:`/`Г3:`; Г8/Г9/Г6 — приоритет 2, следующий заход).

## Четыре правила

### 1. Append-only события — для полей, где реально задают ретро-вопрос

Не для всего мутируемого — граница проходит по тому, спрашивают ли
когда-нибудь «как это менялось со временем», а не просто «что сейчас».
На 2026-08-14 список полей, которым это применимо:

| Поле | Статус |
|---|---|
| Цена продажи (`apartment_listings.price`) | ✅ есть — `price_history` |
| Цена аренды (`rental_listings.price`) | ✅ есть — `rental_price_history` |
| Цена юнита застройщика (`newbuild_units.price`) | ✅ есть — `newbuild_unit_price_history` |
| Просмотры (`apartment_listings.views_count`) | ✅ сделано 2026-08-14 (Г2) — `views_history` |
| Статус объявления (active/archived) | ⏳ Г1, не в приоритете 1/2 — предложение осталось: `status_history`, если подтвердится, что архивация на Krisha не терминальна |
| Текстовые поля ЖК (описание/фото-набор) | ⏳ Г4, приоритет 2 не включает явно — распространяется вместе с Г8 (`source_changes`) |
| Официальные данные КЖК (`homeportal_objects`) | ⏳ Г10, приоритет 2 (частично, вместе с Г8) |

Паттерн (используется единообразно во всех трёх реализованных случаях):
таблица `<entity>_history(entity_id, old_value, new_value, changed_at)`
ИЛИ `<entity>_history(entity_id, value, observed_at)`, если «не
изменилось» — тоже значимая точка (просмотры, воздух, хайп — где график
строится по наблюдениям, не только по изменениям); текущее значение
остаётся в основной таблице как быстрый read-path, история — рядом, не
вместо.

### 2. `updated_at`/`computed_at` — на всё мутируемое

Даже там, где полноценная история избыточна (правится редко, вручную —
`complex_tech_specs`, `complex_materials`). Различие двух имён —
намеренное, не синонимы:
- `updated_at` — когда ЗНАЧЕНИЕ последний раз менялось (ручная правка,
  апсерт с новыми данными).
- `computed_at` — когда его последний раз ПЕРЕСЧИТАЛИ, даже если
  результат оказался тем же (агрегаты, скоры) — честно отвечает «на
  сколько это свежо», не «когда оно физически поменялось в последний
  раз» (эти два вопроса для агрегата — разные: `avg_price_m2` мог не
  измениться 3 цикла подряд, но это не значит, что его не пересчитывали).

**Урок Г3** (заложен в дизайн новой таблицы `complex_stats_history`
прямо при её создании 2026-08-14, не постфактум): любая НОВАЯ таблица
снимков/агрегатов проектируется с `computed_at` С САМОГО НАЧАЛА. Прямое
следствие для очереди: `complex_location_scores` (`scoring_roadmap.md`,
Часть 3, п.9, ещё не реализовано) обязана иметь `computed_at` в
исходной схеме — если её спроектируют как обычный overwrite без
таймстампа «на живую», тот же класс гэпа появится на новой таблице в
день её создания, а не через полгода эксплуатации.

### 3. `observed_at` — на каждое СОБРАННОЕ (не вычисленное) значение

Отдельно от `updated_at`/`computed_at` (те — про мутацию/пересчёт
СВОЕЙ записи), `observed_at` — про то, когда СИСТЕМА В ПОСЛЕДНИЙ РАЗ
ПРОВЕРЯЛА источник, независимо от того, изменилось ли что-то. Разница
принципиальна для внешних коллекторов: `views_count_updated_at`
(апартаменты) — по названию читается как «когда значение поменялось»,
а фактически означает «когда в последний раз проверяли» — эти два
вопроса легко перепутать, что и стало исходным поводом для Г2. Новые
поля/таблицы, собирающие внешние данные, должны называть это поле
`observed_at` явно (как в `views_history`, `air_stations.ts`,
`hype_location_history.ts`), не перегружать `updated_at` этим смыслом.

### 4. `raw` параллельно с `normalized` — кэш на TTL, не архив навечно

Не архитектурная норма по умолчанию (дорого: место + поддержка), а
осознанное решение для дорогих/редких/нестабильных источников. Модель —
`osm_cache` (JSONB ответа Overpass, ключ — сетка+вид данных, TTL по
`fetched_at`) и `newbuild_units.raw_json` (сырой ответ застройщика,
хранится с самой строкой, не отдельной таблицей — единица сбора и так
редкая и ценная, шахматка обновляется раз в неделю).

Когда оправдано:
- Источник дорогой/редкий по вызовам (Overpass, LLM-анализ, детальный
  скан застройщика) — переразбор без похода в сеть экономит реальные
  деньги/время/вежливость.
- Формат источника нестабилен (сайт застройщика меняет вёрстку) —
  raw-снимок позволяет чинить парсер задним числом на уже собранных
  данных, не жданая новый обход.

Когда НЕ оправдано (не заводить просто по аналогии):
- Дешёвые частые источники, где нормализованное значение и есть весь
  ценный сигнал (воздух, курс НБРК) — RAW тут не даёт ничего сверх
  `normalized`-снимка с `observed_at`.

## Как применять к новым таблицам (чеклист при проектировании)

1. Это агрегат/скор, который пересчитывается периодически? →
   `computed_at` обязателен (правило 2), подумать про историю снимков
   по правилу 1, если ожидается вопрос «как менялось».
2. Это результат внешнего сбора (парсер/API/LLM)? → `observed_at`
   обязателен (правило 3), явно назвать так, не `updated_at`.
3. Собираемое значение может реально меняться со временем и на это
   МОГУТ спросить «а как это выглядело раньше»? → append-only история
   рядом с текущим значением (правило 1), не overwrite.
4. Источник дорогой/редкий/нестабильный по формату? → рассмотреть
   `raw`-кэш с TTL (правило 4), не хранить только `normalized`.
5. Ничего из выше не подходит (правится вручную, редко, история не
   нужна) → достаточно `updated_at`, не усложнять.

## Связь со scoring-блоком

Данные, собранные с `observed_at`, но пока НЕ используемые в скоринге
(`views_count`/`views_history` — Г2) — кандидаты на включение в Deal
Score после накопления истории (`scoring_audit.md` §5.4 уже отметил
`views_count` как «собран, но не используется»). Решение об
использовании — отдельным заходом, после того как гейт Г2 (7 дней,
покрытие) даст первую содержательную выборку; включение самого сигнала
в формулу — по тем же правилам гейта, что волна 1/2 скоринга (отчёт
распределения до/после, топ-20 movers), не автоматически по факту
наличия истории.
