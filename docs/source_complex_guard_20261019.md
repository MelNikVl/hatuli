# Проверка исходного имени ЖК перед подборкой — 19.10.2026

Статус: реализация в отдельной ветке; публикация и общий CI фиксируются ниже после проверки.

## Почему выбран этот шаг

В свежем отчёте обнаружено расхождение: источник объявления 1012143050
показывает «Акерке 2», сохранённая привязка — 3119 «Возрождение».
Одинаковый адрес не подтверждает алиас. Неправильная принадлежность опасна
не только в карточке: объявление может исказить сравнение цен других квартир.
[P1 №81](https://github.com/MelNikVl/hatuli/issues/81) остаётся открытым.

Первичные источники, проверены 19.10.2026:

- [Krisha — оценка](https://krisha.kz/valuation/): продукт использует параметры
  квартиры и похожие объявления, объясняет зависимость результата от точности
  данных и числа аналогов. Это заявленные свойства конкурента, не наш аудит его точности.
- [Zillow — Zestimate](https://www.zillow.com/zestimate/): характеристики,
  источники и сопоставимые объекты входят в оценку; диапазон передаёт
  неопределённость, недостаточно надёжных данных может препятствовать публикации.

Вывод для Хатули: укреплять идентичность до ценового сравнения. Это продуктовый
вывод из двух официальных описаний, не измерение всего мирового рынка или
новый статистический вывод о ценах Казахстана. Прогноз цены сделки и срока
продажи без временной проверки и подтверждённых исходов не добавляется.

## Контракт

1. Пакетный read-only читатель получает исходный ключ `a.complex_name` для
   всех способов привязки. До рейтинга и медиан он должен совпасть с именем
   канонического ЖК или однозначным проверенным алиасом. Сам redirect не
   подтверждает новое написание. Неподтверждённое/пустое имя связанного ЖК исключается.
2. Свежая квитанция обычного браузера содержит `source_complex_name`:
   строку видимого структурированного поля ЖК либо явный `null`, когда
   такого поля нет. Пропущенное поле не означает отсутствие ЖК.
   Описание, соседние объявления, адрес и префикс имени не заменяют это поле.
3. При наличии квитанции конфликт имени, архив или изменившиеся цена,
   комнаты, площадь/этаж исключают строку **до первого расчёта** и из пула аналогов.
   Публикация требует свежих квитанций; прежний HTTP-путь не обходит проверку.
4. Зонтик сам по себе не устанавливает дом. Для корпуса сохраняются
   самостоятельные доказательства `address`/`token`; географическая близость
   их не заменяет. У непривязанного объекта допустимо только явное отсутствие
   ЖК в квитанции, без придуманной каталожной принадлежности.
5. Старые квитанции не дополняются из каталога. Файлы квитанций и внутренние
   ключи не копируются в публичную карточку. Издатель не меняет БД/алиасы/привязки.

## Измерение и границы

Read-only срез: 20 880 строк, по старому identity gate допускались 14 472,
по новому — 14 190. Дополнительно исключены 282 строки. Всего флаг
расхождения исходного имени установлен у 1450 строк; часть уже отсекалась
другими условиями. Это изменение допуска, а не измеренная точность каталога.

**Известный P1 не считается полностью исправленным.** У 1012143050 сохранённое
имя уже равно ошибочному каноническому. Без свежей квитанции с реальным именем
оно проходит проверку БД. С квитанцией «Акерке 2» новая проверка его исключит.
Непосещённые аналоги остаются под проверкой БД и не объявляются проверенными
сегодня в браузере. Нужен отдельный постоянный учёт конфликтов источника
на уровне объявления и пересмотр ошибочной привязки. Очередь алиасов/дубликатов
ЖК для этого не переиспользована: её рескор может автоматически подтвердить
связь другого назначения. Общий market-comparison и аренда этим изменением
не переводятся на новую проверку; снимки сегодняшних подборок не перепубликуются.

Тесты используют синтетические данные и запрещают подключения к PostgreSQL;
проверка SQL на живой БД выполнялась только read-only. Проверенная метрика
людей/день и поисковых переходов по-прежнему отсутствует. Цель 1000 пользователей
в день не объявляется достигнутой. Следующие приоритеты: постоянная очередь
конфликтов объявлений, baseline посещаемости и поисковой видимости.
