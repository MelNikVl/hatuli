# Сценарный калькулятор срока экспозиции — follow-up к аудиту

Дата: 2026-08-21. Статус: **реализовано и подключено к UI**. Продолжение
[`dom_forecast_audit.md`](dom_forecast_audit.md) (тот документ не менялся —
его вывод про log-normal AFT остаётся в силе, см. п.0 ниже).

## 0. Что НЕ изменилось

`dom_forecast_audit.md` остаётся верным как есть: log-normal AFT на этих
данных — MAE 229.6 дня против 15.1 у сегментного baseline, quality gate не
пройден, «Пауза по ML» (`verdict_strategy.md`) действует до ~2026-09-14.
Этот документ НЕ пересматривает то решение и не переобучает AFT.

## 1. Что реализовано вместо AFT

Задача явно требует «не останавливайся снова только с аудитом» —
реализован **непараметрический** эмпирический калькулятор
(`bot/analytics/dom_scenario.py`), а не ML-модель:

- Kaplan-Meier по сегменту (`district × rooms`, с фоллбэком до городского
  baseline) — та же непараметрическая альтернатива, которую аудит указал
  как «не пробовалась в этом заходе» (§5 п.4 аудита).
- PAVA (pool adjacent violators) — монотонное сглаживание ценовых корзин
  внутри сегмента, вместо AFT-регрессии на `price_dev`.
- Единица наблюдения — `property_id` (Property Identity), активные
  объявления — right-censored, `archived_at` НЕ трактуется как
  подтверждённая продажа — все три принципа те же, что в аудите.

Это не обучаемая модель: нет весов, которые сохраняются/версионируются
между запусками, нет градиентного спуска — просто описательная статистика
(выборочная функция дожития + изотоническая регрессия) поверх текущих
данных при каждом расчёте (с TTL-кэшем, не «обучение»). «Пауза по ML» не
нарушена.

## 2. Честный backtest — реальные числа

`scripts/dom_scenario_backtest.py` (не переписывает и не трогает
`scripts/dom_forecast_baseline_backtest.py` — отдельный скрипт, та же
временная схема backtest, импортирует `_fetch_rows`/`_build_records`/
`_baseline_segment_median` оттуда напрямую, не дублирует). Прогон на тех же
данных/cutoff (`2026-08-01`), что и оригинальный аудит:

```
train N=25603 (event=2152, censored=23451); честный test N=806
Сегменты, выбранные для test-записей: {'district_rooms_bucket': 799, 'city_rooms_bucket': 7}
Метод предсказания: {'segment_median_baseline': 806}

Kaplan-Meier + fallback:  MAE=15.17 дн  medAE=13.0 дн  pred range=[11.0, 39.0]
Baseline (сегм. медиана): MAE=15.16 дн  medAE=13.5 дн

MONOTONICITY CHECK: проверено 20 записей, нарушений монотонности: 0
```

**Честный вывод: новый метод НЕ превосходит baseline** — MAE 15.17 vs
15.16 (разница ~0.015 дня, статистически неотличимо), а в 806 из 806
test-случаев расчёт вообще свёлся к тому же самому `segment_median_
baseline`-фоллбэку, что и раньше (KM ни разу не набрал `MIN_EVENTS_FOR_KM=8`
событий в сегменте на cutoff-дату — то же 90%+ цензурирование и короткое
окно, что уже объяснило провал AFT в основном аудите). Это НЕ провал в
духе AFT (в 10-17 раз хуже) — это **тот же порядок точности**, что и
проверенный baseline, потому что при этом объёме данных метод честно
деградирует до него же, а не выдумывает более точный ответ, которого
данные не поддерживают.

**Не заявляем, что модель стала точнее baseline** (прямое требование
задания, §5) — она статистически эквивалентна ему на исторических данных.
Причина подключить её к UI, а не остановиться повторно с «недостаточно
данных»: (а) прямое указание задания — «даже если новый метод не
улучшает baseline, реализуй UI на честном baseline как ориентировочный
сценарный расчёт с низким уровнем надёжности»; (б) метод даёт **диапазон**
(не точку) и **сценарии по цене** (то, чего вообще не было у
baseline-скрипта — тот считал только MAE одной точки), с явной пометкой
надёжности «низкая» именно в случаях, где сработал fallback (что сейчас
почти всегда — см. `method` в ответе API).

На боевых (не cutoff-урезанных) данных сегодня (2026-08-21) событий в
сегментах уже больше, чем было на дату cutoff (`2026-08-01`) — часть
сегментов в реальном времени пересекает `MIN_EVENTS_FOR_KM` и получает
`confidence: "sufficient"/"medium"`, а не только фоллбэк (см. тесты в
`tests/test_dom_scenario.py`, где на синтетическом сегменте с 12+
событиями расчёт проходит без insufficient_data). Числа backtest выше —
консервативная нижняя граница на исторических данных трёхнедельной
давности, не текущее состояние.

## 3. Что показывает пользователю UI

Диапазон, не точное число, с явной пометкой надёжности и обязательной
оговоркой «снятие объявления с публикации не подтверждает факт продажи»
— см. `CONFIRMED_SALE_DISCLAIMER` в `bot/analytics/dom_scenario.py` и
блок «📈 Ожидаемый срок экспозиции» в попапе объявления
(`bot/templates/dashboard.html::openDetailModal`). Полная разбивка
критериев/API — докстринг `bot/analytics/dom_scenario.py`.

## 4. Пересмотр в будущем

Тот же критерий, что в §5 п.1-3 `dom_forecast_audit.md`: по мере
накопления `outcome_labels`/окна наблюдения `MIN_EVENTS_FOR_KM` будет
достигаться чаще, `confidence` будет расти от `low` к `medium`/
`sufficient` сам по себе, без изменений кода — `scripts/dom_scenario_
backtest.py` можно перезапускать на актуальных данных для контроля.
