## Почему прежняя очистка не решила проблему

В проекте уже есть достаточный фундамент:

| Механизм | Существующая реализация |
|---|---|
| Устойчивый ID ЖК | `complexes.id` |
| Перенаправление дубля | `complexes.canonical_id`, миграция 101 |
| Зонтики и части | `parent_complex_id`, `is_umbrella`, миграция 054 |
| Связь объявления с ЖК | `apartment_listings.complex_id`, миграция 100 |
| Внешние идентификаторы | `complex_source_links` |
| Проверенные отношения | `complex_relations`, миграция 095 |
| Журнал привязки | `listing_complex_resolution_log`, миграция 096 |

Но разные части приложения используют разные ключи. `complex_binding`
возвращает канонический ID, а каталог, карточки, координаты, ежедневные
снимки и часть Property Identity продолжали искать исходный текст имени.
Поэтому исправление ID не гарантировало единую карточку или статистику.

Другие подтверждённые дефекты исходного кода:

* Общая ссылка Крыши плюс произвольный префикс имени могли свести
  «Нурсая» и «Нурсая 2» либо «Arena» и «Arena Towers».
* Повторяющееся имя при поиске префикса выбиралось по порядку строк.
* Обрывок текста мог стать каноном для другого обрывка.
* `complex_relations` не участвовал в автоматической канонизации.
* Дом под зонтиком выбирался по одному номеру без улицы, по первому
  совпавшему токену корпуса или ближайшей точке без проверки конкурента.
* В геопривязке две записи одного канонического ЖК считались двумя
  конкурирующими объектами.

## Что исправлено в этом изменении

1. Канонизация допускает только явные варианты имени; сохраняет номера
   и различающие части. Дома с `parent_complex_id` не сводятся с зонтиком.
   Обрывок не становится канонической записью. Неоднозначное имя не
   выбирается по порядку. Отрицательные reviewed relations блокируют
   прямые и транзитивные объединения.
2. House resolution проверяет улицу вместе с номером. Несколько текстовых
   кандидатов не разрешаются выбором первого. Для гео нужен отрыв 15 м
   от второго кандидата; коллизии участков остаются внутри своей группы.
3. Геопривязка считает расстояния до различных канонических ID.
4. Публичный каталог и точки карты скрывают aliases и несопоставленные
   обрывки; поиск по alias находит канонический ЖК. Старая ссылка на alias
   ведёт в каноническую карточку с прежними фильтрами.
5. Продажи, адрес и наблюдаемый центроид карточки используют общий
   membership: явный ID имеет приоритет, старое имя используется только
   при отсутствии ID и отсутствии неоднозначности. Зонтик агрегирует
   дочерние объекты; карточка ребёнка сохраняет отдельный состав. Этот же
   состав используют графики цены и ухода объявлений продажи, счётчики
   детей и «Дом неизвестен».
6. Ежедневный `complex_stats_history` использует ID и canonical aliases,
   не размножает объявления JOIN по неоднозначному имени. Снимки домов
   остаются отдельными от зонтика. Старые исторические строки не переписываются.
7. Добавлен read-only аудит и SELECT-preview binding; аудит не вызывает
   `init_pool`, не применяет миграции и работает в read-only транзакции.

Это исправление правил и нескольких потребителей. Оно не является
завершённой очисткой реального справочника: без данных нельзя утвердить,
что конкретные два ЖК являются дублями, очередями или соседями.

## Модель, которую нужно довести до конца

**Один физический ЖК может иметь несколько зданий, адресов и имён.**
Разные адреса сами по себе не означают разные ЖК; одинаковый адрес сам
по себе не доказывает один ЖК. Зонтичный бренд не доказывает физическую
идентичность проектов. Для разных частей общего проекта сохраняем
отдельные ID и связь с родителем.

Достаточно расширить существующую схему, сохранив ID и source spine:

| Дополнение | Содержимое и правило |
|---|---|
| `complex_aliases` | `complex_id`, исходное имя, нормализованный ключ, источник, evidence, reviewer/time; один ключ может указывать на несколько ЖК |
| `complex_addresses` | `complex_id`, исходный адрес, город, ключ улицы, номер/литера, при необходимости ID дочернего здания, источник, evidence, статус проверки; несколько строк на ЖК |
| Утверждённый canonical mapping | Отдельный manual mapping/journal, который автоматический `apply_canonical` не перезаписывает; причина и обратимый manifest |
| Полный журнал переходов | Старый и новый ID, включая новый NULL, основание, версия resolver; текущая 096 не позволяет фиксировать отвязки из-за NOT NULL |

Не надо создавать отдельный ЖК на каждое написание. Нормализация убирает
регистр, кавычки, служебное «ЖК» и лишние пробелы, сохраняя номера, очереди,
корпуса, East/West и другие различия. Транслит и fuzzy дают кандидатов;
утверждённое соответствие/внешний ID/адресное доказательство дают решение.

Пример желаемого поведения: «Tumar Club», «Тумар Клаб» и «ЖК Тумар Клаб»
могут стать aliases одного подтверждённого ID. По сведениям пользователя
реальный адрес Tumar Club — Анет баба, 4; Туркестан, 4Б нужно расследовать
как конфликт источников, а не исправлять только точку на карте. Отдельную
очередь Tumar нельзя включать в этот ID без подтверждения отношения.

## Выполнение на сервере

1. Сверить `git rev-parse HEAD`, `git status --short`, действующие сервисы
   и применённые миграции. Работать в отдельном worktree; незакоммиченные
   изменения production не затирать.
2. До подключения нового canonicalizer к работающему `service_geobind`
   снять аудит из текущей БД. Сам новый код на отдельной ветке не меняет
   production, но после deployment штатный geobind начнёт пересчёт.

```bash
venv/bin/python scripts/audit_complex_identity_current.py --output /tmp/complex_identity_audit.json
venv/bin/python scripts/audit_complex_identity_current.py --output /tmp/complex_identity_binding_preview.json --binding-preview
```

`--binding-preview` проверяет привязку с **текущей сохранённой canonical
map**, а не с предложенными изменениями из первого раздела отчёта.
Для плана «после канонизации» нужна копия БД или отдельная shadow map.
Счётчики direct-bound в отчёте также не заменяют полный impact manifest.

3. Разделить найденные группы на `duplicate_same_complex`,
   `renamed_same_complex`, `sibling_phase`, `same_umbrella_project`,
   `separate_neighbor_complex` и ещё не проверенные. Использовать уже
   существующие review dataset/tool/import-preview скрипты. Положительные
   reviewed relations в этом патче сами не создают canonical redirects.
4. Для каждого предлагаемого изменения подготовить полный список
   affected complex/listing/property ID, before/after values, SQL preview
   и rollback. Сначала 10–20 подтверждённых групп, затем повторный аудит.
5. Сделать общий resolver внешних ID/проверенных aliases/адресов и
   перевести на него ingest. `ensure_complex` больше не должен терять
   последующие адреса через `COALESCE` одного поля.
6. Довести оставшихся потребителей: Property Identity и market-profile,
   метрики и центроид карты ЖК, фильтры аналитики, аренда, текущие cached
   `complexes.listings_count/avg_price_m2`, читатели истории снимков зонтика.
   Там ещё есть raw-name/raw-ID пути. Storage снимков остаётся по отдельным
   домам; reader общего зонтика должен агрегировать с корректными весами.
7. После утверждённой перепривязки пересчитать текущие метрики и снимок
   за сегодня. Исторические агрегаты не суммировать вслепую: они уже
   агрегированы и могут содержать пересечения. Ретроспективный пересчёт
   — из истории исходных объявлений и утверждённой политики идентичности.

## Проверка результата

* Дубликаты имени открывают одну карточку; ID и ссылки сохраняются.
* Несколько адресов не создают несколько физических ЖК автоматически.
* Разные очереди и соседние ЖК не сливаются по похожему имени/ссылке.
* Зонтик показывает общий состав без двойного подсчёта; каждый ребёнок — свой.
* Явная связь ID сильнее устаревшего текстового имени.
* Неоднозначный адрес или соседние точки остаются на проверке.
* Количество исходных объявлений сохраняется; rollback восстанавливает связи.
* Проверенный manual mapping сохраняется после каждого geobind/reimport.

Наблюдаемый центроид ещё не является проверенной геолокацией здания.
Фильтрация пространственных выбросов и provenance координат остаются
отдельным обязательным пунктом перед исправлением карт вроде Tumar Club.
