# Аудит и прототип прогноза срока экспозиции при разных ценах

Дата: 2026-08-21. Статус: **аудит + baseline + честный backtest — ЗАВЕРШЕНЫ.
API/UI — НЕ реализованы: quality gate не пройден** (см. §5). Read-only:
ничего не изменяет в проде, не пишет в БД.

## 0. Важный найденный контекст — «Пауза по ML»

Перед прототипированием обнаружен **уже действующий, задокументированный
запрет** на обучение ML/статистических предсказательных моделей в этом
проекте: [`verdict_strategy.md` §«Пауза по ML»](verdict_strategy.md)
(датирован 2026-08-14, действует **до ~2026-09-14** — то есть ещё
**~3 недели от даты этого аудита**):

> Фазы C и D НЕ запускаются до: (1) накопления `views_history` ≥30 дней,
> (2) накопления `deal_score_snapshots` ≥30 дней, (3) перепроектирования
> Фазы C вокруг предсказания исхода... **Запрещено: обучение ML-моделей.**

Прогноз срока экспозиции по цене — это ровно то, что документ называет
«Фазой C» (предсказание исхода, не цены — см.
[`liquidity_model_design.md`](liquidity_model_design.md)). Freeze введён
НЕ произвольно: даже зрелый, несколько раз пересчитанный `price_score`
(предсказание куда более простой бинарной задачи — «исчезнет ли
объявление за 30 дней») честно (temporally-safe) даёт AUC только
**≈0.71–0.72** (`verdict_strategy.md` §«Фаза A.5 — результаты честного
backtest»). Это независимое от данного аудита подтверждение того же
вывода, к которому пришёл baseline ниже (§5): данных пока физически не
хватает на надёжную регрессию срока экспозиции.

**Вывод**: даже без собственного прототипа ниже, продолжать в API/UI
означало бы нарушить уже принятое, обоснованное архитектурное решение
проекта. Прототип (§3-5) сделан ВСЁ РАВНО — по прямому заданию задачи
(«сначала аудит... затем baseline и честный backtest») и чтобы дать
количественное, не только процедурное обоснование — и он независимо
подтверждает тот же вывод.

## 1. Аудит существующих данных/расчётов

|---|---|---|---|

Из них с известным `time_on_market` — только **2**. **Как учтены активные объявления и повторные публикации**: активные
(`is_active=TRUE`, исход ещё не наступил) входят в выборку как
**right-censored** наблюдения — время цензурирования = `as_of − first_seen`,
`event=0`. Повторные публикации — группировка по `property_id`
(см. таблицу выше); при >1 listing на property берётся последний по
`first_seen` как «текущее» представление объекта (при текущей почти
нулевой доле релистов выбор метода не влияет на результат).

## 2. Формулы

- `price_at(listing, as_of)` = последний `price_history.new_price` с
  `changed_at ≤ as_of`, иначе `price_history` самого раннего изменения
  `.old_price`, иначе текущая `apartment_listings.price` (изменений не
  было) — идентично `bot/analytics/market_dashboards.py`.
- `price_dev` = `ln(price_per_m2) − ln(медиана price_per_m2 сегмента
  район×комнатность на as_of-безопасных данных)`.
- Модель: **log-normal AFT** (accelerated failure time) с
  right-censoring, оценка максимального правдоподобия (`scipy.optimize`,
  тот же класс инструментов, что уже использует `baseline_measure.py` —
  numpy/scipy, без sklearn/pandas — их нет в окружении и это соответствует
  стилю проекта):
  - `T` (дни) ~ LogNormal(Xβ, σ²)
  - Наблюдаемое событие: `log f(t) = logφ((ln t − Xβ)/σ) − ln t − ln σ`
  - Censored: `log S(t) = logΦ̄((ln t − Xβ)/σ)`
  - Признаки `X`: intercept, `price_dev`, `ln(площадь)`, (в полной версии
    добавлены район/комнатность/этаж/первичка — см. §4, убраны в
    экономной версии из-за коллинеарности с `price_dev`)

## 3. Baseline и честный временной backtest

Скрипт: [`scripts/dom_forecast_baseline_backtest.py`](../scripts/dom_forecast_baseline_backtest.py)
(read-only, ничего не пишет, можно перезапустить на актуальных данных).

**Схема backtest — временная, не случайная**:
- `cutoff = 2026-08-01`.
- **train**: все `property` с `first_seen < cutoff`. `event=1` только
  если `archived_at < cutoff` И `time_on_market` уже известен на cutoff
  (2152 наблюдения). Иначе `event=0` (censored), `T = cutoff − first_seen`
  (23 451 наблюдение) — это ЧЕСТНО то, что было бы известно, стоя на
  `cutoff`, не более.
- **test**: та же выборка (`first_seen < cutoff`), но которая **реально
  разрешилась ПОСЛЕ cutoff** (807 наблюдений) — сравниваем прогноз,
  сделанный на `cutoff`-знаниях, с ФАКТИЧЕСКИМ исходом, узнанным только
  сейчас. Ни один признак теста не использует данные после `cutoff`.
- Сегментные медианы цены/м² — посчитаны **только на train-периоде**.

## 4. Результаты (реальные данные, не иллюстративные)

| Модель | MAE (дней) | medAE (дней) | Комментарий |
|---|---|---|---|
| **Baseline** — медиана DOM по сегменту (район×комнатность), train-период | **15.1** | 13.5 | Медиана истинного DOM в тесте ≈22 дня — MAE 15 дней ≈ 68% относительной ошибки, тоже посредственно, но на порядок стабильнее |
| AFT, полный набор признаков (район+комнатность dummy + `price_dev` + первичка + этаж) | 261.4 | 171.0 | intercept/price_dev/primary коэффициенты нестабильны — `primary` (мало наблюдений после разбивки) даёт множитель ×18 |
| AFT, экономный набор (`price_dev`+`ln(площадь)` только) | 229.6 | 166.1 | Прогнозы 2–2336 дней (6+ лет) на объектах, где факт — 11–55 дней |
| AFT, экономный + L2-регуляризация (λ=1…200) | 165–230 | — | Регуляризация не спасает — MAE не опускается ниже ~165 дней ни при каком λ; это НЕ проблема переобучения весов, а структурная проблема самой модели в этом режиме данных |

**AFT в любой протестированной конфигурации в 10–17 раз хуже тривиального
сегментного baseline.**

**Почему** (диагностика, не гипотеза): цензурирование — **90%+** (2152
события на 25 603 наблюдений), а окно наблюдения (весь `apartment_listings`
существует ~11 недель, `cutoff`-train — и того короче) **сопоставимо по
масштабу с самим хвостом распределения** срока экспозиции, который модель
пытается оценить. Лог-нормальное MLE в этом режиме систематически
переоценивает медиану, экстраполируя по цензурированным (ещё не
завершившимся) наблюдениям — типичная и известная патология AFT/survival
моделей при коротком окне относительно масштаба распределения, не баг
реализации (проверено: полная и экономная спецификации, 6 уровней
регуляризации — везде тот же порядок ошибки).

Калибровка (Brier score, 30/60/90 дней) на этом же test-наборе тоже
неинформативна: test-выборка по построению состоит ТОЛЬКО из объектов,
которые уже разрешились (иначе неоткуда взять «истинный» DOM для
сравнения) — Brier тут искусственно занижен смещением выборки, честная
калибровка потребовала бы отдельного, более сложного протокола (все
объекты, доживших до дня X, независимо от исхода) — не стал строить его
поверх уже проваленной по MAE модели.

## 5. Решение — quality gate НЕ пройден

Оба независимых источника сигнала (§0 — существующий honest AUC
Deal Score ≈0.71-0.72 на более простой задаче; §4 — собственный
прототип, 10-17× хуже тривиального baseline) указывают на одно: **на
2026-08-21 данных недостаточно для надёжного прогноза срока экспозиции
по цене**. По прямому указанию задачи («Если данных недостаточно или
модель не проходит проверку — показывать «Недостаточно данных», не
выдумывать прогноз») — **API/UI не реализованы**.

### Что нужно, чтобы пересмотреть решение
1. Дождаться конца паузы по ML (~2026-09-14) и накопления
   `views_history`/`deal_score_snapshots` ≥30 дней (уже запланировано
   независимо от этой задачи).
2. Дать `outcome_labels` набрать заметно больше завершённых наблюдений
   (сейчас 3686 всего, из них 2152 доступно train-периоду backtest) —
   счётчик растёт естественно со временем, отдельных действий не
   требует.
3. Переоценить эту же схему backtest (скрипт готов и переиспользуем)
   при более длинном train-окне — если MAE приблизится к baseline
   (или превзойдёт его), тогда переходить к API/UI по плану задания
   (§6-7 исходного задания).
4. Рассмотреть непараметрическую альтернативу (Kaplan-Meier по сегменту
   вместо параметрического AFT) как менее чувствительную к короткому
   окну — не пробовалась в этом заходе (baseline §4 — по сути её
   упрощённый эквивалент — уже использована как контрольная точка).

## 6. Архитектурные требования, если решение будет пересмотрено

Зафиксировано на будущее, не реализовано сейчас:
- Расчёт — отдельным офлайн-джобом (по аналогии с `deal_score_snapshots`/
  `hex_market_stats_snapshot.py`), не при каждом запросе страницы.
- Версионирование модели + дата расчёта — тот же паттерн, что уже есть
  у `deal_score_snapshots.score_version`/`git_commit`.
- Кеш на готовые прогнозы (TTL, как у `bot/analytics/market_dashboards.py`).
- Никакого N+1 — один агрегирующий запрос на страницу/попап, не по
  объявлению.
- Текст пользователю (уже согласован, готов к переиспользованию, когда
  модель будет готова): «Ожидаемый срок экспозиции при текущей цене:
  X–Y дней». Подпись: «Прогноз основан на сроках активности похожих
  объявлений. Выбытие объявления не подтверждает факт продажи».
