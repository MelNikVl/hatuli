# Фаза C/D: модель ликвидности — отчёт (2026-10-02)

Вход: [`liquidity_model_design.md`](liquidity_model_design.md), [`verdict_strategy.md`](verdict_strategy.md) §5 (Фазы C/D), §8 (гейт).
Код: `bot/core/liquidity_features.py`, `bot/core/liquidity_model.py`, `liquidity_train.py`,
`liquidity_predict.py`, миграция `097_liquidity_predictions.sql`; исследование — `research/phase_c/`.

## 1. Главная находка до модели: метка исхода была неверной

`apartment_listings.is_active = TRUE` на 2026-10-02 стоит у ~107K объявлений, а живых на Крыше
~19K (полный круг deep sweep — 958 страниц × 20). ~67K «активных» не видели в выдаче >14 дней,
archive-check проверил ~9K. Следствие: `archived_at`/`outcome_labels.disappeared_within_30d`
систематически недосчитывают уходы, и честный AUC ≈ 0.72 из Фазы A.5/B мерился на зашумлённой метке.

**Новая метка — по `last_seen`.** Deep sweep видит каждое живое объявление раз в ~1.5–2 дня
(`DEEP_SWEEP_CIRCLE_DURATION_SEC` = 33.5 ч на последнем круге), поэтому `last_seen < t0 + H` =
«пропало из выдачи за H дней». Популяция на t0: не-дубли, `first_seen ≤ t0`, `last_seen ≥ t0`.
До 2026-09-28 поиск шёл с потолком 80 млн и только с фото — для окон до этой даты популяция
ограничена покрытым сегментом (иначе last_seen не обновлялся и «уход» ложный).

На этой метке **сырой `price_score` даёт AUC ≈ 0.53** (exit14) и **≈ 0.51** (cut30) — почти
случайно. 0.72 был артефактом метки, а не силой цены.

| метка | смысл | доля |
|---|---|---|
| `exit14` | пропало из выдачи за 14 дней | 23–36% (по t0) |
| `exit14_clean` | то же, но без релиста (та же квартира под новым id: комнаты, ±1 м², тот же дом/<150 м и этаж, или тот же не-generic продавец) | 14–16% |
| `cut30` | снижение цены за 30 дней | 24–26% |

~30% уходов за 30 дней — перевыставления. **Уход ≠ продажа**; данных о сделках нет.

Артефакт: 2026-09-26/27 — пик last_seen (~2.5K объявлений не видели с тех пор). Окна,
захватывающие эти даты, исключены из исследовательской оценки (exit30 на t0=08-29 не использован).

## 2. Утечки, найденные и закрытые

Поля карточки, которые парсер **дописывает после t0**, давали ложный прирост AUC:

* `year_built` объявления — дозаполняет `coord_backfill` задним числом: +0.03 AUC на exit14;
* `kitchen_area`, `ceiling_height`, `finish_level`, `renovation`, `building_type`, длина описания,
  число фото, планировка — перезаписываются detail re-fetch'ем, который триггерится **сменой цены**:
  `kitchen_area` один давал +0.06 AUC на cut30.

Критерий: разница доли NULL между классами исхода > 2 п.п. при том, что поле — не снимок на t0.
Все такие поля исключены (докстринг `liquidity_features.py`, тест `test_backfilled_card_fields_not_used`).
Год дома — из `complexes.year_built` (уровень дома, не дописывается по объявлению).

## 3. Ablation study (финальный набор признаков)

Протокол: t0 = 2026-08-15 / 08-22 / 08-29 (exit14, exit14_clean) и 08-15 / 08-22 (cut30);
LightGBM; (а) **group-CV** — StratifiedGroupKFold(5) по `listing_id`; (б) **temporal** — обучение
на t0=08-15, тест на более позднем t0 **только по новым объявлениям** (`first_seen > 08-15`).
Bootstrap CI (paired, 300) на разницу AUC.

### exit14 (уход за 14 дней), n = 52 165

| блок | CV AUC | Δ к пред. (CI95) | temporal 08-22 | temporal 08-29 |
|---|---|---|---|---|
| baseline: сырой `price_score` | 0.530 | — | 0.556 | 0.524 |
| + price (Deal Score, отклонения) | 0.559 | | 0.555 | 0.528 |
| + DOM / история цены | 0.609 | +0.044…+0.054 | 0.571 | 0.555 |
| + просмотры / RDI | 0.622 | +0.010…+0.016 | 0.581 | 0.559 |
| + продавец | 0.644 | +0.020…+0.025 | 0.608 | 0.589 |
| + конкуренция | 0.642 | ≈0 | 0.610 | 0.596 |
| + объект / дом | 0.645 | +0.002…+0.008 | 0.600 | 0.596 |
| + локация | **0.645** | ≈0 | **0.612** | **0.601** |

### exit14_clean (уход без релиста — ближе к продаже)

CV 0.601, но **temporal 0.549 vs baseline 0.556 (08-22) и 0.543 vs 0.528 (08-29)** — на честном
holdout модель не бьёт baseline. **Гейт не пройден — в прод не идёт.**

### Что двигает ликвидность (ответ на вопрос §8 дизайна)

1. **DOM и история цены** — самый сильный блок (+0.05).
2. **Продавец** (собственник/агент, сколько объявлений под именем) — +0.02…0.05.
3. **Просмотры / RDI** — +0.01…0.02 (покрытие просмотрами только ~40% популяции).
4. Конкуренция, объект/дом, локация — около нуля сверх уже имеющегося.
5. Цена относительно рынка сама по себе почти ничего не предсказывает.

## 4. Гейт и решение

| модель | CV vs baseline (CI95 разницы)¹ | temporal | гейт | в прод |
|---|---|---|---|---|
| `exit14` | 0.661 vs 0.527 (+0.129…+0.139) | 0.60–0.61 vs 0.52–0.56 | ✅ | да |
| `cut30` | 0.664 vs 0.506 (+0.150…+0.165) | 0.625 vs 0.493 | ✅ | да |
| `exit14_clean` | 0.601 vs 0.530 | 0.54–0.55 ≈ baseline | ❌ | нет |

¹ Прод-сборщик признаков (`liquidity_train.py --dry-run`, t0 до 2026-09-12) воспроизводит
исследовательские числа (08-15: 0.645 vs 0.640).

Честная оценка: AUC 0.60–0.66 — **слабый-умеренный** сигнал. Полезен для ранжирования
(«скорее уйдёт/подешевеет, чем типичное»), не для точных обещаний. Поэтому в UI — вероятность,
перцентиль, причины и явная оговорка, **без изменения `score_total`** (freeze §6) и без замены
существующего breakdown-попапа.

## 5. Фаза D — что сделано

* `liquidity_predictions` (миграция 097) — append-only журнал прогнозов по дням (`p_exit14`,
  `p_cut30`, перцентили, причины, версии моделей) — для будущей честной проверки.
* `liquidity_train.py` (таймер пн 07:15) — переобучение на всех t0 с наблюдаемым исходом; новая
  версия активируется **только при пройденном гейте**, иначе остаётся прежняя.
* `liquidity_predict.py` (таймер ежедневно 09:30, после снапшотов) — прогноз для живых объявлений
  (`last_seen ≥ сегодня−3`).
* Модалка объявления — блок «📈 Прогноз ликвидности (бета)»: вероятности, перцентиль, топ-3
  причины (SHAP-вклады LightGBM), оговорка «уход ≠ продажа».

## 6. Не сделано / дальше

* **P(продажа)** — нет надёжной метки. Нужны данные о сделках или ручная разметка
  («продано» vs «снято/перевыставлено»).
* **`is_active` в `apartment_listings` неверен для ~85% строк** — отдельная задача (архивация по
  `last_seen` или расширение archive-check). Влияет на UI, на `get_comparables()` (аналоги из
  «мёртвых» объявлений) и на `outcome_labels`.
* Property Episode ID (§3 дизайна) — релист-детектор здесь эвристический, только для метки.
* Покрытие просмотрами ~40% — расширение `service_viewcount` усилит блок views.
* `views_history` хранит одну строку на объявление (не историю) — используются `listing_snapshots.views`.
