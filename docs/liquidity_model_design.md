# Модель ликвидности следующего поколения — архитектура Фазы C

Дата: 2026-08-14. Статус: черновик — архитектурный вход для перепроектированной
Фазы C (см. [«Пауза по ML»](verdict_strategy.md#пауза-по-ml-2026-08-14--2026-09-14)
в `verdict_strategy.md`: Фаза C не запускается до накопления данных и
переосмысления вокруг предсказания исхода, не цены). Этот документ — НЕ
план спринта с датами, НЕ код: карта признаков и решений, из которой
Фаза C будет собираться, когда пауза закончится.

Контекст, зачем это вообще нужно — честный итог Фазы B
([«Анализ потолка price_score»](verdict_strategy.md#анализ-потолка-price_score-фаза-b-2026-08-14)):
`comparable_score` v2 не поднял AUC — bottleneck не в качестве пула
аналогов, а в том, что `price_score` в одиночку близок к потолку
предсказания исчезновения (~0.72). Документ ниже — гипотеза о том, что
двигает потолок дальше: не «более точная цена», а «признаки, которых у
price_score нет в принципе» (спрос, конкуренция, продавец, объект, ЖК,
локация, рыночный момент).

---

## 1. Разделение ликвидности

Одна и та же квартира может быть **структурно ликвидной** (типовая
планировка, средний метраж, хороший ЖК, удобная локация — то, что не
меняется день ото дня) и при этом **не продаваться месяцами**, потому
что продавец назначил цену на 20% выше рынка. И наоборот — неудобная
студия у дороги может уйти за неделю, если её оценили честно и продавец
готов торговаться.

- **Структурная ликвидность** — свойство ОБЪЕКТА, почти не меняется во
  времени: тип квартиры (блок 4), характеристики ЖК/дома (блок 5),
  локация (блок 6). Отвечает на вопрос «для этой категории квартир
  вообще есть массовый спрос?».
- **Текущая рыночная ликвидность** — свойство МОМЕНТА: цена
  относительно рынка (блок 2), конкуренция здесь и сейчас (блок 3),
  поведение самого объявления (блок 1), продавец (блок 7), рыночный
  контекст (блок 9). Отвечает на вопрос «уйдёт ли ИМЕННО ЭТО объявление
  быстро при текущей цене и текущем состоянии рынка?».

Текущий `price_score` (Фаза A-B) — чистый сигнал текущей рыночной
ликвидности по ОДНОЙ оси (цена). Модель следующего поколения — это не
замена price_score, а `Liquidity = f(структурная составляющая,
рыночная составляющая)`, где price_score остаётся одним из входов
(см. §10).

## 2. 9 блоков признаков (по приоритету)

Приоритет — не порядок реализации (для этого есть Ablation Study, §8),
а порядок по ожидаемой силе сигнала и/или дешевизне получения.

### 2.1 Поведение объявления
`views_total`, `views_1d`/`3d`/`7d`/`14d` (кумулятивно и в окне),
velocity (просмотров/день), acceleration (ускоряется/затухает
интерес), `views_vs_similar` (см. RDI, §4), DOM (days on market),
история изменений цены (частота, направление, кумулятивный %).
Данные: `views_history` (Г2, собирается с 2026-08-14),
`price_history` (собирается давно, уже сильный источник).

### 2.2 Цена vs рынок
Отклонение от аналогов, перцентиль в своём сегменте, динамика market
reference во времени. Это и есть сегодняшний `price_score` —
единственный блок с уже измеренным honest AUC (~0.72, Фаза A.5/B).

### 2.3 Конкуренция
N активных аналогов прямо сейчас, скорость появления новых
(предложение растёт/падает), скорость исчезновения аналогов (рынок
горячий/холодный — та же идея, что уже использует `analyze_bargain()`
через `old_listings_ratio`, но как явный признак, не только для
текстовой рекомендации), DOM аналогов. Данные: частично уже есть
(`hex_market_stats.listings_count`, Фаза L1) — гранулярность гексагона,
не «прямых аналогов», нужно уточнение до уровня сопоставимого пула
(`bot/core/bargain.py::get_comparables()`/`comparable_score.py`).

### 2.4 Тип квартиры
Комнаты, площадь, этаж (и этаж/этажность — не сырой этаж), планировка
(студия/распашонка/линейка — частично уже определяется в
`listing_intel.py`/AI-анализе), год постройки, ремонт (`finish_level`,
уже есть), санузлы, балкон, парковка (частично есть на уровне ЖК —
`complexes.has_parking`, не на уровне квартиры).

### 2.5 ЖК/дом
Класс, рейтинг, застройщик (`developers` — уже есть таблица с
`score_total`/`avg_delay_months`/`has_court_cases`), возраст, состояние,
лифты, паркинг, документы.

**Важно (структурная поправка перед использованием `complexes` как
источника «ЖК»)**: `complexes` (2079 активных записей на дату
документа) — это в подавляющем большинстве **ДОМА** (один адрес), не
ЖК в бытовом смысле. Настоящий ЖК — «зонтик» (`is_umbrella=true`,
обычно несколько корпусов/очередей под одним брендом, застройка после
~2000г.) — таких сейчас **8**, и под ними **33** дома
(`parent_complex_id IS NOT NULL`). Остальные ~2038 записей —
самостоятельные дома без зонтика (не обязательно ошибка: у многих
домов правда нет «зонтичного» ЖК-бренда, особенно у вторички/советского
фонда). Для признаков блока 5 это значит: агрегаты уровня «ЖК»
(рейтинг, застройщик, документы) корректны для дома под зонтиком ТОЛЬКО
если унаследованы от зонтика (`parent_complex_id`), а для
самостоятельного дома — это и есть его собственный уровень, отдельного
«ЖК» над ним нет. Путать эти два случая — тот же класс риска, что уже
несколько раз ловился в проекте (House-resolution, `resolve_complex_
geo_centroid()`, `complex_stats_snapshot.py` — везде понадобился явный
`resolved_house_id`/`parent_complex_id`-приоритет, не поиск «вслепую»).

### 2.6 Локация
Транспорт, школы/сады, магазины, парки, шум, воздух, плотность
застройки. **Фаза L1 уже собирает** большую часть (`complex_location_
scores`, `hex_market_stats`) — прямой вход, не с нуля (см. §10). Воздух
— НЕ подключён к этому слою (см. отдельный аудит качества воздуха,
2026-08-14: инфраструктура для воздуха в проекте есть — `air_stations`/
`air_quality_astana`/`air_grid` — но не как фактор локационного скора
ЖК, только как отдельная тепловая карта в дашборде; интеграция в
`bot/core/location_score.py` как 6-й источник — не рассмотрена в Фазе
L1, кандидат для Фазы L3 или отдельного захода).

### 2.7 Продавец

**✅ Реализовано (задача 2026-08-15)**: `seller_profiles` (миграция 077)
— агрегация на уровне продавца, которой в проекте не было вообще.
Ежедневный пересчёт — `seller_profile_snapshot.py`
(`krisha-seller-profile.timer`, после `krisha-listing-snapshot.timer`
08:30 и `krisha-outcome-labels.timer` 08:45). Метрики: `active_listings_
count`/`total_listings_count`, `relist_count`/`relist_rate` (через
`outcome_labels.relisted_within_60d`), `price_cut_count`/`price_cut_rate`
(через `price_history`), `avg_days_to_sell` (среднее `time_on_market` по
архивным), `median_discount_pct` (`statistics.median()` по
`bargain_discount_pct` текущих листингов продавца — тот же метод, что
`deal_score.py`), `is_high_relist_rate` (`relist_rate>0.3` И
`total_listings_count>=3` — анти-шумовой порог поверх заданного в задаче
условия, 1 релист из 1 объявления не паттерн), `is_motivated_seller`
(2+ снижения цены за последние 30 дней по всем листингам продавца
вместе), `is_ambiguous` (миграция 079, см. ниже). UI — блок
«🧑 Продавец» в модалке объявления (`dashboard.html`, данные из
`bot/core/listing_detail.py`): тип+активные, 🔴 частые релисты,
🟢 мотивированный продавец, ⚠️ >50 активных (похоже на агентство),
⚠️ общее имя (`is_ambiguous`, вместо мотивированного/релист-бейджей).

**Ключ агрегации — решённый вопрос, с оговоркой**: `seller_name`
(нормализованный: trim+lower+схлопнутые пробелы), НЕ телефон.
Подтверждено пользователем 2026-08-15: `apartment_listings.seller_phone`
не существует — телефон продавца нигде не парсится (Krisha прячет номер
за JS-кнопкой «Показать номер» с отдельным AJAX-запросом, парсинг
телефона — отдельная будущая задача, не эта). `seller_name` — рабочий,
но заведомо шумный идентификатор:
- **Generic-заглушки** ("хозяин" — 1120 объявлений на живых данных,
  "продавец" — 219, "хозяйка" — 254 и т.п.) — это НЕ один продавец, это
  роль-заглушка тысяч разных людей. Такие имена целиком исключены из
  агрегации (стоп-лист в `seller_profile_snapshot.py`), не просто
  скрыты в UI — иначе `active_listings_count` под "хозяин" мгновенно
  ложно триггерил бы бейдж «агентство >50 активных» на каждом таком
  объявлении.
- **Частые личные имена** ("Асель" — 168 объявлений, "Динара" — 166,
  "Айгуль" — 160...) собственным решением НЕ исключены из агрегации
  целиком — это осмысленные имена, среди них попадаются и настоящие
  высокообъёмные продавцы (например "Ультаракова Асемгуль" — 77
  объявлений, судя по числу и типу realtor, похоже на одного реального
  риелтора), которые стоп-лист терять не должен. Но подавляющее
  большинство таких строк — коллизия РАЗНЫХ реальных людей с одинаковым
  именем: на живых данных (до миграции 079) 837 из 1249 сработавших
  `is_motivated_seller` относились к продавцам с
  `total_listings_count>5`.

  **✅ Исправлено (миграция 079, задача 2026-08-15, тот же день)**:
  `is_ambiguous BOOLEAN` (`total_listings_count>15`) — не просто текстовая
  оговорка в UI, а жёсткое правило на уровне снапшота
  (`seller_profile_snapshot.py::_aggregate()`): для `is_ambiguous=TRUE`
  `is_high_relist_rate`/`is_motivated_seller` принудительно `FALSE`,
  даже если сырые `relist_rate`/число недавних снижений формально
  проходят пороги — на выборке из >15 вероятно разных людей эти
  поведенческие выводы про ОДНОГО продавца не значат ничего. Эффект на
  живых данных: `is_motivated_seller` сработал 894 раза вместо 1249
  (528 продавцов помечены `is_ambiguous`); `is_high_relist_rate`
  (24 случая) не изменился — реальные релистеры почти всегда с малым
  числом листингов, крупные собирательные имена усредняются к базовому
  уровню и так. Сами числа (`relist_rate`/`price_cut_rate`) НЕ занулены
  — это честная статистика по строке-имени, занулён только вывод
  «это поведение ОДНОГО продавца». Известная цена решения: настоящие
  высокообъёмные продавцы (та же "Ультаракова Асемгуль", 77 объявлений
  >15) тоже теряют оба флага — простой порог не отличает "один активный
  риелтор" от "15+ разных людей с одинаковым именем", без телефона
  отличить нечем в принципе.

### 2.8 Качество объявления
Фото (количество, качество — есть ли вообще), описание (длина,
информативность — частично уже AI-анализируется, `ai_text_analysis.py`),
полнота полей (сколько ключевых полей заполнено — близко к идее
`deal_confidence`/«полнота данных», §4 `verdict_strategy.md`, но для
ОБЪЯВЛЕНИЯ, не для скора).

### 2.9 Рыночный контекст
Сезон, день недели, общий объём предложения по городу/сегменту, темп
сделок (косвенно — темп исчезновения активных объявлений по городу).
Самый «внешний» блок — не про конкретный объект/ЖК, про рынок целиком.

## 3. Property Episode ID

Одна физическая квартира может пройти через несколько `listing_id`
(релист после снятия, новое объявление после смены агентства/цены).
Без объединения таких `listing_id` в один «эпизод» метрики вроде DOM
или числа релистов систематически занижаются — уже известная проблема
в проекте (см. §3.5 `verdict_strategy.md`, "`disappeared_within_30d` ≠
продажа" — тот же корень: не различаем «ушла с рынка» от «появилась
заново под другим id»).

Жизненный цикл эпизода: `appeared → views → price change(s) →
reduction → relist → new price → disappeared`.

Даёт: `true_DOM` (не по одному listing_id, а по всей цепочке),
`relist_count`, `cumulative_views` (сумма по всем listing_id эпизода),
`cumulative_price_reduction` (от самой первой цены эпизода до
последней). Метод — де-дупликация квартир по времени, тот же класс
задачи, что решает арбитраж дублей в реальном времени (`dedup.py`/
`dedup_listings.py`), только не «на лету» при парсинге, а ретроспективно
для склейки истории (arXiv 2004.02706 — тот же общий подход к proptech
duplicate/relist detection).

**Не с нуля** — в проекте уже есть ПОЛОВИНА этого механизма:
`outcome_labels_recompute.py` уже детектирует релисты
(`relisted_within_60d`/`possibly_relisted`, строгое совпадение
ЖК+комнаты+площадь+цена±10%/дата, ослабленное — без цены/даты).
Property Episode ID — это тот же матчинг, но развёрнутый в
ПОСТОЯННУЮ сущность (`property_episode_id`, живёт в `apartment_
listings` или отдельной связующей таблице), не разовый признак в
`outcome_labels`, плюс агрегация `cumulative_views`/`cumulative_price_
reduction` по цепочке, которой сейчас нет вовсе.

## 4. Relative Demand Index (RDI)

```
RDI = views_per_day(объект) / median(views_per_day(сопоставимые))
```

Абсолютные просмотры малоинформативны (топовый ЖК получает больше
просмотров просто по факту популярности бренда, не по факту
ликвидности конкретной квартиры) — относительный показатель к
сопоставимым (тот же пул, что уже строит `bargain.py::get_comparables()`/
`comparable_score.py`) сильнее как сигнал спроса. RDI > 1 — спрос выше
среднего по сегменту, < 1 — ниже. Требует `views_history` (собирается)
+ определения «сопоставимых» (уже есть механизм).

## 5. Competition metrics

```
Supply Pressure = N_active_comparables
Demand/Supply    = views_of_comparables / active_comparables
```

Supply Pressure — сколько прямых конкурентов у объявления прямо
сейчас (не гексагон целиком — именно сопоставимый пул). Demand/Supply
— грубая аппроксимация «сколько внимания достаётся на каждого
конкурента» — высокое значение = дефицит предложения при живом
интересе (рынок продавца), низкое = избыток при вялом интересе (рынок
покупателя). Оба — прямое продолжение блока 3 (§2.3), формализованные
в явные признаки.

## 6. Buyer Pool Size

Аппроксимация размера пула потенциальных покупателей для данного типа
квартиры: частота этого типа на рынке (комнатность×площадь-бакет) ×
скорость исчезновения объявлений этого типа × ценовой диапазон, в
который попадает объект.

Идея: ликвиднее обычно МАССОВЫЙ тип (например 2к/55м²), не «лучший»
(5к/240м²) — у элитных больших квартир меньше потенциальных
покупателей физически (доход, размер семьи, назначение), даже если
объект объективно качественнее. Это прямо объясняет, почему
`price_score` (цена относительно похожих) не ловит этот эффект —
похожие квартиры МОГУТ быть все одинаково неликвидны, если весь
сегмент маленький, а цена относительно них при этом «средняя».

## 7. Юридические риски первички

Источник: `developers.kz`, фильтр «способ привлечения денег
дольщиков». Три независимых механизма защиты дольщика (действующие в
РК одновременно, не альтернативы друг другу):

- **БВУ** (участие банка второго уровня) — стройку финансирует банк,
  застройщик работает на кредитные/проектные деньги банка, не только
  на деньги дольщиков напрямую.
- **КЖК** (гарантия Казахстанской жилищной компании) — государственная
  гарантия по договору долевого участия.
- **МИО** (разрешение местного исполнительного органа/акимата) —
  формальное разрешение на привлечение денег дольщиков по этому
  конкретному проекту.

**Отсутствие всех трёх у строящегося объекта — красный флаг** (не
обязательно мошенничество, но означает: юридической защиты дольщика по
этому конкретному стандартному пути нет, риск выше среднего).

В проекте уже есть таблица `developers` (score_total/score_delivery/
score_quality/score_financial, `has_court_cases`, `avg_delay_months`,
`projects_delayed`) — это ДОПОЛНЯЕТ её, не дублирует: `developers` —
репутация застройщика в целом (по прошлым проектам), БВУ/КЖК/МИО —
юридический статус КОНКРЕТНОГО текущего проекта (может быть новый
застройщик без истории, но с полным набором защит — или наоборот).

**UI**: переводить в человеческий вид, не показывать сырые
аббревиатуры без объяснения — например «🟢 Гарантия КЖК», «🟡
Разрешение акимата (МИО) есть, банк не участвует», «🟢 Участие банка
(БВУ)». Тот же принцип, что уже применяется к бейджам «Orda Plus»/
парковка на странице ЖК (`complex_detail.html` — цветные пилюли с
понятной подписью, не код/аббревиатура как есть).

**✅ Реализовано (задача 2026-08-15, коммиты в два захода)**: КЖК-часть
источника подключена как отдельный слой, не встроена в этот раздел

## 11. Эвристика класса старого фонда — ПРОВЕРЕНА, эффект меньше заявленного

Предложенное правило: `year_built < 2000 AND housing_class IS NULL →
эконом`, обоснование — «~95% домов старше 2000 года в Астане —
советский фонд, по умолчанию эконом».

**Проверка по факту (2026-08-14, живая БД) не подтверждает масштаб
эффекта:**

| Срез (`complexes`, `is_garbage=false`) | n |
|---|---|
| Всего без `housing_class` | 1837 |
| ...из них БЕЗ `year_built` вовсе (эвристика неприменима) | 298 |
| ...из них С `year_built`, но **`year_built >= 2000`** | **1505** |
| ...из них С `year_built < 2000` (эвристика применима) | **34** |

Из 1539 записей с известным `year_built`, но без `housing_class`,
**97.8% — POST-2000**, не pre-2000. Это структурно объяснимо: Астана
стала столицей в 1997-98г. и застраивалась в основном ПОСЛЕ этого —
довольно молодой город, советский фонд в базе `complexes` — не
большинство, а меньшинство. Заявленная предпосылка «~95% старше 2000»,
похоже, была общим представлением о жилом фонде постсоветских городов
вообще, не проверенным для конкретно этой базы.

**Вывод**: эвристика сама по себе не ошибочна — для тех самых 34
записей (`year_built < 2000`, класс не указан) присвоить «эконом» по
умолчанию разумно и низкорискованно. Но она закрывает **34 из 1837** (≈1.9%)
дыры покрытия класса, не «основную дыру», как предполагалось.
**Основная дыра — 1505 post-2000 записей без класса** — для них нужен
другой источник: либо `housing_class_model.py` (Фаза B, уже обучена на
`avg_price_m2`+`year_built`, применяется ко всем комплексам с
известными признаками — уже частично закрывает именно этот случай,
см. `predicted_housing_class` в §10), либо расширение ручной разметки.

**Рекомендация**: применить эвристику как есть для 34 pre-2000 записей
(дёшево, обоснованно) — но не рассчитывать, что она заметно улучшит
общее покрытие класса для стратификации аналогов; основную работу уже
делает `housing_class_model` (Фаза B), не эта эвристика.
