## B. Расшифровка 130 "истинного残атка" (должен был совпасть, не совпал)

Порядок bootstrap исключён как причина: во всех сэмплированных парах
property "другой" стороны существовала ЗАДОЛГО до bootstrap'а listing'а
"этой" стороны (`property_listings.linked_at`/`properties.created_at`
проверены напрямую) — `_generate_candidates()` ищет "уже существующие
properties" на момент СВОЕГО bootstrap'а, значит должна была найти её.

**Найдена сильная корреляция с `matcher_version`** (версия правил,
которыми был сделан bootstrap каждой стороны — `candidate_only_v1` до
2026-08-17, `candidate_only_v2` после, см. докстринг `_MATCHER_VERSION`
в `property_linker.py`):

| `matcher_version` A / B | N | Доля |
|---|---|---|
| v2 / v1 (новая сторона позже v1-property) | 85 | 65% |
| v1 / v1 (обе стороны СТАРЫЕ, из bulk-бэкфилла) | 33 | 25% |
| v1 / v2 | 8 | 6% |
| v2 / v2 (обе новые) | 4 | 3% |

**65% (85/130)** приходится на пары, где "новая" (v2) сторона должна была
найти "старую" (v1) property — SQL самого `_find_fuzzy_properties`/
`_find_exact_hash_properties` НЕ фильтрует по `matcher_version` (прочитан
код, подтверждено), так что формально запрос должен был вернуть строку.
Точный механизм, ПОЧЕМУ он этого не сделал (кэш bootstrap-индекса? Другой
код-путь у bulk backfill vs incremental job? Гонка между параллельными
прогонами?) — **НЕ изолирован до конца в рамках этого захода** —
требует построчной отладки `scripts/backfill_property_ids.py` (bulk,
"two-phase deterministic construction", создавал `v1`-properties) в паре
с `bot/jobs/property_identity_incremental.py` (создаёт `v2`). Честно
помечено как открытая находка, не выдано за решённую.

**25% (33/130)** — ОБЕ стороны `v1`, то есть обе, вероятно, из ОДНОГО
bulk backfill прогона — это ОТДЕЛЬНАЯ причина от version-boundary теории
выше (не может объясняться "новый код не видит старые properties", раз
обе стороны старые) — похоже на самостоятельный гэп ВНУТРИ
`backfill_property_ids.py`'s "two-phase" построения (первая фаза строит
кандидатов "в моменте", возможно НЕ на полный текущий снапшот
`properties`, если строилась батчами). Тоже требует отдельной построчной
проверки.

**Рекомендация**: НЕ чинить эвристически. Прочитать `scripts/
backfill_property_ids.py` целиком (вне бюджета этого захода) прежде чем
делать выводы о причине — это реальный, подтверждённый количественно
(130 пар) гэп кандидат-генератора, но точный механизм не варьируется наугад.

## C. 185 (пересчитано: свежее число ниже) сломанных `duplicate_of` ссылок

- **Когда возникла ссылка**: 100% в июне-августе 2026, ДО применения
  `migrations/089_archive_no_hard_delete.sql` (применена 2026-08-17
  22:54:04 — самый конец периода).
- **Существовал ли target когда-либо**: **11/185** (6%) найдены в
  `price_history` (доказательство, что listing реально существовал и имел
  хотя бы одно изменение цены). 0/185 в `listing_snapshots`/
  `listing_archive_history` — обе таблицы моложе, чем момент удаления
  этих записей, отсутствие там ожидаемо, не противоречит гипотезе.
- **Можно ли восстановить**: НЕТ для подавляющего большинства — данные
  физически удалены (hard delete) под СТАРОЙ (уже исправленной)
  политикой. `price_history`-запись восстанавливает только ФАКТ
  существования + цены на момент событий, не сам listing целиком
  (адрес/фото/продавец физически потеряны).
- **Влияние на метрики**: эти 185 связей НАВСЕГДА останутся "orphan" в
  Property Identity candidate graph — не баг Property Identity, а
  необратимое следствие СТАРОЙ политики удаления на ДРУГИХ данных,
  исправленной миграцией 089 уже ПОСЛЕ того, как эти конкретные записи
  пострадали. Новых таких потерь возникать не должно (миграция 089 —
  no-hard-delete, только архивирование).
